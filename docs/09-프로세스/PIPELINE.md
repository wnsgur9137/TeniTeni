# 12. 개발 파이프라인

`/pipeline` 커맨드가 따르는 규약입니다. 절차는 `.claude/commands/pipeline.md`, 규약은 이 문서입니다.

## 12.1 10단계

| # | 단계 | 조건부 | 산출물 |
|---|---|---|---|
| 1 | 현재 작업 상황 파악 | — | 열린 이슈·마일스톤 진행률 |
| 2 | 예정 작업 파악 | — | 후보 이슈 목록 |
| 3 | 진행 작업 확정 | — | 이슈 선택 + `⏳InProgress` 라벨 |
| 4 | 레퍼런스 확인 | ✅ | `docs/08-레퍼런스/` 갱신 |
| 5 | 기존 설계 파악 | — | (읽기만) |
| 6 | 기획서 작성·검증 | ✅ | `docs/07-기획/SPEC-NNNN-*.md` |
| 7 | 디자인 작성·검증 | ✅ | 디자인 캔버스 Artifact |
| 8 | 개발·검증 | ✅ | 코드 + 게이트 통과 |
| 9 | commit → PR → 리뷰 → 반영 | — | `/ship --from=2` 위임 |
| 10 | 병합 | — | `--merge` 옵션에 따름 |

## 12.2 작업 상태 — GitHub Issues

**Issues가 단일 진실 공급원입니다.** 문서에 작업 상태를 두지 않습니다.

| 항목 | 규칙 |
|---|---|
| 이슈 크기 | **1~2일치.** PR이 300~600줄에 들어오게 |
| 마일스톤 | **Phase 하위 단계** (`0-A 정찰`, `0-C 검증`, `1-B 스윙 검출`…) |
| 진행률 | GitHub 마일스톤이 자동 집계 — 1단계가 읽는 값 |
| 동기화 | **단방향.** WORK-PLAN → 마일스톤·이슈. 문서는 계획만 갖고 상태를 갖지 않는다 |

> WORK-PLAN·ROADMAP에서 체크박스를 제거했습니다. 수동 동기화는 반드시 깨집니다 — 도입 전 ROADMAP은 28 미완 / 1 완료였으나 실제로는 0-A가 병합된 상태였습니다.

### 라벨 체계 — 2축

한 축으로는 단계를 가릴 수 없습니다. 디자인 필요 여부는 **area**가, 기획서·레퍼런스 필요 여부는 **type**이 결정합니다.

#### type 축 — 기존 이모지 라벨을 그대로 사용

`Pooing-iOS` 등 다른 개인 프로젝트와 공유하는 컨벤션입니다. **파이프라인이 여기에 맞춥니다.**

| 라벨 | 매트릭스상 type |
|---|---|
| `✨Feature` | `feature` |
| `🐞Bug` · `🔨BugFix` · `🔥HotFix` | `bugfix` |
| `♻️Refactor` | `refactor` |
| `📃Docs` | `docs` |
| `⚙️Setting` | `chore` |

나머지 이모지 라벨(`🤖AI` `🛰️API` `📦Dependency` `🌍Deploy` `🔔FBEvent` `➰Duplicate` `❓Question` `✅Test` `🔖Version` `🚫DoNotMerge`)은 **보조 분류**이며 매트릭스 판정에 쓰지 않습니다.

#### area 축 — 이 프로젝트에서 신설

기존 체계에 없던 축입니다. 디자인 단계 판정에 필요합니다. **type 축과 같은 이모지 컨벤션을 씁니다.**

| 라벨 | 의미 |
|---|---|
| `📱UI` | 화면이 있는 iOS 작업 |
| `🧩Core` | TeniVision·카메라·동시성 등 **화면 없는** iOS 작업 (0-A가 여기) |
| `☁️Backend` | FastAPI·워커·DB |
| `🧠ML` | 모델·학습·평가 |
| `📃Docs` | 문서 — **기존 type 라벨을 재사용** |

> `📃Docs`는 **type과 area 양쪽에 속하는 유일한 라벨**입니다. type 해석 시 다른 type 라벨(`⚙️Setting` 등)이 함께 있으면 그쪽이 우선하므로 모호하지 않습니다.
> 예: `⚙️Setting` + `📃Docs` → type=chore, area=docs. `📃Docs` 단독 → type=docs, area=docs.

#### 보조

| 라벨 | 의미 |
|---|---|
| `⏳InProgress` | 파이프라인 3단계에서 부여. 재개 판정의 근거 |
| `🚧Blocked` | 선행 조건 미충족. 후보에서 제외하되 사유를 표시 |

> 파이프라인 도입 시 `type:*`·`area:*` 라벨을 새로 만들었다가, 기존 이모지 라벨과 중복되거나 컨벤션이 어긋나 모두 이모지 체계로 재작성했습니다. **기존 컨벤션이 먼저이고 파이프라인이 거기 맞추는 것**이 맞습니다.

#### 라벨 신설 금지

파이프라인은 **위 목록에 없는 라벨을 새로 만들지 않습니다.** 분류가 부족하면 규약을 먼저 고칩니다.

## 12.3 단계 실행 매트릭스

`1·2·3·5·9·10`은 항상 실행합니다. 가변은 `4·6·7·8`입니다.

| type 라벨 | area | 4 레퍼런스 | 6 기획서 | 7 디자인 | 8 개발 |
|---|---|---|---|---|---|
| `✨Feature` | `📱UI` | ✅ | ✅ | ✅ | ✅ |
| `✨Feature` | `🧩Core` | ⚪ | ✅ | ❌ | ✅ |
| `✨Feature` | `☁️Backend` | ⚪ | ✅ | ❌ | ✅ |
| `✨Feature` | `🧠ML` | ✅ | ✅ | ❌ | ✅ |
| `🐞Bug` `🔨BugFix` `🔥HotFix` | 전부 | ❌ | ⚪ | ❌ | ✅ |
| `♻️Refactor` | 전부 | ❌ | ⚪ | ❌ | ✅ |
| `📃Docs` | 전부 | ❌ | ❌ | ❌ | ❌ |
| `⚙️Setting` | 전부 | ❌ | ❌ | ❌ | ✅ |

### 조건부(⚪) 판정 기준

| 단계 | 실행 조건 |
|---|---|
| 4 레퍼런스 (`🧩Core`/`☁️Backend`) | 사용자에게 보이는 동작이 있을 때. 순수 내부 구조면 생략 |
| 6 기획서 (버그·리팩터) | 원인이 불명확하거나 2일 이상 걸릴 때. 명백한 버그는 이슈 본문으로 충분 |

### 라벨 누락 시

3단계에서 추론해 제안하고, 승인 시 `gh issue edit --add-label`로 부여한 뒤 진행합니다. **라벨이 없다고 멈추지 않습니다.**

## 12.4 4단계 — 레퍼런스

### 대상

| 앱 | 참고 지점 |
|---|---|
| **SwingVision** | 가장 직접적 경쟁. iOS 네이티브, 온디바이스 분석, 코트 인식·인아웃 |
| **Zepp Tennis** | 센서 기반. 영상으로 푸는 것을 IMU로 푼 사례 — 지표 정의 |
| **Onform** | 영상 코칭. 리플레이·주석 UX |
| **Hudl Technique** | 스포츠 일반 폼 분석. 페이즈 스크러버 |

`🧠ML` 작업은 앱이 아니라 **논문·구현체**를 봅니다 (`docs/08-레퍼런스/ml/`).

### 목적과 한계

**"무엇을 어떻게 해결했는가"를 파악하는 것**이 목적입니다. 시각적 모방은 하지 않습니다 — 특정 회사의 독자적 UI 패턴 재현은 금지입니다.

조사 수단(웹·스토어 페이지)의 한계상 실제로 얻을 수 있는 것은 **지표 정의 · 기능 범위 · 사용자 불만**입니다. 인터랙션의 결이나 반응 속도는 알 수 없으므로 그렇게 기대하지 않습니다.

### 방법과 누적

1. `claude-in-chrome`으로 스토어 페이지·리뷰 확인
2. 확장이 동작하지 않으면 **`WebFetch`로 자동 전환** — 도구 문제로 파이프라인을 막지 않는다
3. `docs/08-레퍼런스/<앱>.md`에 섹션 추가, 프론트매터 `researched` 갱신

**재조사 주기 3개월.** `researched`가 3개월 이내면 기존 문서를 읽고 통과합니다.

## 12.5 6단계 — 기획서

`docs/07-기획/SPEC-NNNN-<slug>.md` (NNNN = 이슈 번호). 이슈 본문에는 요약 3줄 + 링크만 둡니다.

템플릿은 [_templates/기획서.md](../_templates/기획서.md)를 씁니다.

### 중복 방지 규칙

**이미 결정된 사항은 재론하지 않고 링크만 겁니다.** 기획서의 "대안 검토"는 **이번 작업 범위 안의 구현 선택지**로 한정합니다. 스택 결정은 [결정 현황](../05-결정/DECISION-LOG.md)이, 구조 결정은 ADR이 이미 담고 있습니다.

### 검증 체크리스트

- [ ] 범위에 "만들지 않는 것"이 명시되어 있는가
- [ ] 완료 기준이 기계적으로 확인 가능한가
- [ ] 영향받는 문서가 나열되어 있는가
- [ ] 미수행으로 남길 항목이 명시되어 있는가
- [ ] 기존 ADR·D-xx와 내용이 중복되지 않는가

### 기획서는 선행 PR로 먼저 병합합니다

검증을 마치면 **기획서만 담은 PR을 만들어 병합한 뒤** 8단계로 갑니다. 코드와 같은 PR에 싣지 않습니다.

```
브랜치  docs/<이슈번호>-spec
게이트  scripts/verify-docs.sh (문서만 — 수십 초)
제목    📃 docs(spec): SPEC-NNNN <제목>
본문    Refs #N  (Closes 아님 — 이슈는 구현이 끝나야 닫힙니다)
```

**왜 나누는가.**

| 근거 | 내용 |
|---|---|
| 순서가 맞습니다 | 기획서는 구현의 계약입니다. 계약이 먼저 확정돼야 구현을 판정할 수 있습니다 |
| 코드 PR이 작아집니다 | SPEC-0005는 159줄로 PR #15의 **30%** 였습니다 |
| 게이트가 빠릅니다 | 문서 게이트만 돌면 수십 초입니다. iOS 게이트는 10분입니다 |
| 되돌리기 쉽습니다 | 기획이 틀렸을 때 코드와 엉키지 않습니다 |

**구현 중 기획과 달라진 점은 코드 PR에서 기획서를 고칩니다.** 선행 PR로 병합된 기획서를 수정하는 작은 diff가 되고, 그 diff 자체가 "무엇이 달라졌는가"의 기록이 됩니다.

## 12.6 7단계 — 디자인

`📱UI` + `✨Feature`에서만 실행합니다.

- [디자인 시스템](../06-디자인/DESIGN-SYSTEM.md)의 토큰만 사용
- 기존 캔버스가 있으면 **갱신**, 새 캔버스를 남발하지 않는다
- [IA-FLOW](../06-디자인/IA-FLOW.md)의 화면 흐름과 어긋나면 IA를 먼저 고친다

### 검증 체크리스트

- [ ] 디자인 시스템에 없는 색·타이포를 새로 만들지 않았는가
- [ ] 오버레이 팔레트와 UI 팔레트를 섞지 않았는가
- [ ] 가짜 iOS 상태 바를 그리지 않았는가
- [ ] 터치 타깃이 44px 이상인가

## 12.7 8단계 — 개발

**코드가 바뀌는 작업이면 항상 반복 개발 모드(OMC Ralph)를 사용합니다.** type이 `📃Docs`인 작업만 제외입니다.

| 항목 | 값 |
|---|---|
| 최대 반복 | **20회** |
| 종료 조건 | **게이트 통과** (경고 0 포함) |
| 상한 강제 | 커맨드가 `.omc/state/ralph-state.json`의 `iteration`을 매 반복 확인해 20 도달 시 `cancel` 호출 |

> 반복 모드의 훅은 자체 카운터(최대 100)를 쓰므로 지정 상한이 반영되지 않습니다. **커맨드가 직접 감시해야** 20회가 지켜집니다.

### 게이트

area 라벨로 스크립트를 고릅니다.

| area | 스크립트 |
|---|---|
| `📱UI` / `🧩Core` | `scripts/verify-ios.sh` |
| `📃Docs` | `scripts/verify-docs.sh` |
| `☁️Backend` | `scripts/verify-backend.sh` (Phase 2에 추가) |
| `🧠ML` | `scripts/verify-ml.sh` (미정) |

**게이트가 없는 영역은 경고 후 통과**하되 PR 본문에 "게이트 없음"을 명시합니다.

### 게이트가 조용히 통과하는 함정

게이트의 실패 양식은 두 가지입니다 — **빨갛게 실패하는 것**과 **돌지 않고 통과하는 것.** 후자가 위험합니다. 실제로 겪은 것을 남깁니다.

| 함정 | 증상 | 원인 | 대응 |
|---|---|---|---|
| **한글 경로가 판정에서 빠진다** | `docs/`를 12개 바꿨는데 `docs: skipped` | git의 `core.quotePath` 기본값이 비ASCII 경로를 `"docs/05-\352\262\260.../x.md"`로 이스케이프. `^docs/` 앵커가 빗나감 | `git -c core.quotePath=false` 고정 |
| **경고 0일 때 스크립트가 죽는다** | 통과 메시지가 안 찍히고 끝남 | `grep`이 0건에 종료코드 1. `set -euo pipefail`이 스크립트를 종료 | 카운트하는 `grep`에 `\|\| true` |
| **툴 경고가 경고 수에 섞인다** | 소스가 깨끗한데 경고 n건 | `appintentsmetadataprocessor` 등이 `warning:`을 출력 | `^/…:행:열: warning:` 형태만 집계 |
| **대상 탐지가 오탐한다** | 해당 없는 모듈을 빌드하려다 실패 | `grep -q "\.mac"`이 주석의 `.mac`에도 걸림 | 선언 줄로 한정 (`^\s*destinations:.*\.mac`) |

**판정 결과를 눈으로 확인합니다.** 게이트가 초록이어도 어떤 잡이 실제로 돌았는지 봐야 합니다.

```bash
gh run view <run-id> --repo wnsgur9137/TeniTeni --json jobs \
  --jq '.jobs[] | "\(.name): \(.conclusion)"'
```

`skipped`가 예상과 다르면 `detect` 잡의 "변경 파일" 출력을 엽니다.

이 저장소는 **문서 폴더명이 전부 한글**이라 경로 판정 버그가 문서 게이트를 통째로 무력화합니다. 경로 필터를 건드릴 때마다 한글 경로로 확인합니다.

## 12.8 9~10단계 — `/ship` 위임

```
/ship --from=2
```

`/ship`이 commit → Draft PR → 리뷰 → 반영 → Ready → 병합을 처리합니다. 재구현하지 않습니다.

### 병합 옵션

| 옵션 | 동작 |
|---|---|
| `--merge=critical` | **기본값.** CRITICAL이 남아 있을 때만 확인 |
| `--merge=auto` | 항상 자동 병합 |
| `--merge=confirm` | 항상 확인 |

셋 다 **게이트 실패 시에는 무조건 중단**합니다.

### PR 규약

[저장소 구조 7.6](../03-기술스택/REPOSITORY.md)을 따릅니다 — Assignee `wnsgur9137`, Draft 생성 후 Ready 전환, merge commit, 병합 후 브랜치 삭제.

### PR 단위 — 작게 가져갑니다

**이슈 1개는 PR 2개로 끝납니다.** 기획서 선행 PR([12.5](#125-6단계--기획서))과 구현 PR입니다. 셋 이상이 필요하면 **이슈를 잘못 잡은 것**이므로 이슈를 쪼갭니다.

#### 작업 중 발견한 범위 밖 결함

| 상황 | 처리 |
|---|---|
| **현재 PR의 게이트·검증을 무력화하는 결함** | 같은 PR에서 고칩니다. 검증되지 않은 채 병합되는 것을 막아야 합니다 |
| 그 외 전부 | **이슈로 등록하고 별도 PR.** 지금 고치지 않습니다 |

판단 기준은 하나입니다 — **"이걸 두면 이 PR이 검증됐다고 말할 수 없는가."** 아니면 미룹니다.

실례: PR #15의 한글 경로 `detect` 버그는 그 PR의 문서 변경을 검증에서 통째로 빼고 있었으므로 포함했습니다. 같은 PR에 넣은 규약 문서 갱신은 그 기준을 통과하지 못했습니다 — 별도 PR이었어야 합니다.

#### 커밋 분할

관심사·계층별로 나눕니다. 여기에 하나를 더합니다.

**순수 파일 이동은 독립 커밋으로 둡니다.** `git mv`만 하고 내용을 고치지 않습니다. 이름변경·`public` 부여·로직 수정을 한 커밋에 섞으면 리뷰어가 "이동은 이동일 뿐"을 확인할 방법이 없습니다.

```bash
git mv a/X.swift b/X.swift   # 커밋 1 — 이동만
# 커밋 2 — 접근 제어자·로직 수정
```

#### 크기

**이름변경 탐지 후 추가 400줄**을 넘으면 CI의 `size` 잡이 경고하고 PR 본문에 사유를 요구합니다. 막지는 않습니다 — 스캐폴딩처럼 쪼갤 수 없는 작업이 있습니다.

세는 것은 **추가 줄뿐**입니다. 삭제는 리뷰 부담이 훨씬 작습니다 — 1000줄을 지우고 10줄을 넣은 PR은 큰 PR이 아닙니다.

```bash
git diff --numstat -M origin/main...HEAD | awk '$1 ~ /^[0-9]+$/ {a+=$1} END {print a}'
```

지금까지 실적: #15 추가 526줄, #10 1402줄, #1 1232줄 — 셋 다 기준 초과입니다. #2·#3·#11~#14는 41~155줄로 전부 통과합니다.

> GitHub이 표시하는 숫자는 이동을 "삭제 + 추가"로 세어 부풀려집니다. PR #15는 표시 725줄, 실제 526줄이었습니다. 크기를 말할 때는 `git diff --shortstat -M` 값을 씁니다.

## 12.9 검증 방식

**체크리스트 자가 검증이 기본입니다.** 각 단계의 체크리스트를 기계적으로 확인합니다.

에이전트 검증(`critic`·`architect`·`code-reviewer`)은 **변경 500줄 초과 시에만 선택적으로** 붙입니다. **실패해도 파이프라인을 중단하지 않습니다** — 이 환경에서 결과 회수가 3회 연속 실패한 이력이 있습니다.

자가 검증에는 작성자=리뷰어 사각이 있습니다. PR 본문과 리뷰 코멘트에 그 사실을 명시합니다.
