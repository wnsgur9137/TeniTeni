# 03. 비전 파이프라인

이 문서는 TeniTeni의 기술적 심장부입니다. 여기서 다루는 문제들이 제품의 성패를 직접 결정합니다.

## 3.1 과제별 난이도

| 과제 | 난이도 | 핵심 이슈 | 담당 |
|---|---|---|---|
| 사람 포즈 추정 | 낮음 | Apple Vision이 Neural Engine에서 거의 무료로 처리 | 온디바이스 |
| 스윙 구간 검출 | 중간 | 임계값 튜닝, 오검출 억제 | 온디바이스 |
| 스윙 유형 분류 | 중간 | 학습 데이터 확보 필요 | 온디바이스 |
| **공 궤적 추적** | **높음** | 공이 10~20px, 모션 블러, 프레임 간 이동량 큼 | 양쪽 |
| 코트 인식 / 인·아웃 | 중간 | 라인 검출 + 호모그래피, 조명 변화에 취약 | 서버 |
| **자세 "교정" 판정** | **최고** | **정답 라벨이 존재하지 않음** | 룰 엔진 → 점진적 학습 |

마지막 항목이 진짜 병목입니다. 자세히 다룹니다 (3.6절).

## 3.2 포즈 추정

### 온디바이스 (실시간)

✅ **확정** — Apple Vision `DetectHumanBodyPoseRequest` (신규 Swift API) — [D-06](../05-결정/stack/D-06-pose-engine.md)

[D-01](../05-결정/stack/D-01-deployment-target.md)에서 타깃을 iOS 26으로 확정했으므로 **신규 Swift API를 쓴다.** 레거시 `VN*` 클래스는 사용하지 않는다.

- 2D 관절 **19개**: nose, leftEye, rightEye, leftEar, rightEar, neck, leftShoulder, rightShoulder, leftElbow, rightElbow, leftWrist, rightWrist, root(골반 중심), leftHip, rightHip, leftKnee, rightKnee, leftAnkle, rightAnkle
- 그룹: face, torso, leftArm, rightArm, leftLeg, rightLeg
- **`detectsHands = true`** 로 손 관절까지 한 요청에서 획득 (holistic body pose). 결과는 `observation.leftHand` / `.rightHand`로 접근
- `struct` + `Sendable` + `async` `perform(on:)` → 프레임 파이프라인에서 actor 격리 우회가 필요 없다
- `HumanBodyPoseObservation`이 `Codable`을 준수하고, `keypoints`를 Core ML 호환 multi-array로 제공한다
- Neural Engine 가속, **외부 의존성 0**
- 출력은 정규화 좌표(0~1, 좌하단 원점) + 관절별 confidence

**테니스 관점에서 `detectsHands`가 중요한 이유**: 라켓을 잡은 손의 손목·손 관절이 그립 형태와 임팩트 순간 분석에 직접 쓰인다. 레거시 API였다면 `VNDetectHumanHandPoseRequest`를 따로 돌려 프레임마다 수동으로 결합해야 했다.

**후보 비교**

| 후보 | 관절 수 | 장점 | 단점 |
|---|---|---|---|
| **Vision (Apple)** | 19 + 손 | 의존성 0, ANE 최적화, `detectsHands`로 손 포함, `Sendable` | **발끝 없음**, 커스터마이즈 불가 |
| MediaPipe Pose (BlazePose) | 33 | 관절 수 많음, 발끝 포함, 크로스플랫폼 | 바이너리 크기 증가, ANE 미활용 |
| MoveNet Thunder (Core ML) | 17 | 빠름 | 정확도가 Vision 대비 우위 없음 |
| YOLO-Pose | 17 | 다중 인물 강함 | 단일 인물 시나리오에 과함 |

> ✅ **확정** — Vision 채택. 발끝 부재는 **발목 중점 대비 골반 수평 이동량으로 근사**한다. Phase 1에서 이 근사가 부정확하면 경량 발 검출 모델 추가를 재검토한다.

### 3D 포즈

🟡 **v2+ 검토** — `DetectHumanBodyPose3DRequest` (iOS 26이라 사용 가능하나 v1 범위 밖)

- 3D 관절 17개, 카메라 상대 좌표
- **실시간 예산에 들어가지 않음.** 리플레이 화면에서 선택된 스윙에만 적용
- 단일 인물 전제, LiDAR 없어도 동작하나 있으면 정확도 향상

3D가 필요한 지표: 어깨-골반 분리각(X-Factor), 라켓 궤적의 깊이 성분, 상체 기울기. 2D만으로는 카메라 각도에 따라 값이 왜곡됩니다.

### 서버 (정밀)

⏸ **보류** — [D-20](../05-결정/stack/D-20-server-ml.md). 후보는 MMPose(ViTPose / HRNet), 3D 리프팅은 MotionBERT 계열

서버 정밀 분석이 실제로 온디바이스 대비 유의미한 개선을 주는지는 Phase 2에서 정량 검증 후 도입합니다. **차이가 작으면 서버 포즈 재분석은 하지 않습니다** (GPU 비용 대비 가치 없음).

## 3.3 스윙 검출 및 분류

### 구간 검출 (Segmentation)

포즈 시퀀스에서 스윙의 시작·끝을 찾습니다.

**1차: 룰 기반 트리거**
```
손목 각속도 > 임계값  AND  손목이 몸통 기준선을 교차  AND  최소 지속시간 충족
→ 후보 구간 [t-2s, t+2s]
```
- 라켓을 든 손(dominantHand)의 손목 관절 속도를 주 신호로 사용
- 어깨 회전 각속도를 보조 신호로 결합
- 히스테리시스로 채터링 방지, 최소 간격(예: 0.8초) 이내 재트리거 차단

**2차: 분류기로 검증**
후보 구간을 스윙 분류기에 넣어 4종 중 하나로 분류되지 않으면(신뢰도 미달) 폐기. 이것이 오검출(공 줍기, 스트레칭, 라켓 돌리기) 억제의 핵심입니다.

### 유형 분류

✅ **확정** — Create ML **Action Classifier** (`MLActionClassifier`) — [D-10](../05-결정/stack/D-10-swing-classifier.md)

- 입력: `HumanBodyPoseObservation.keypoints` (Core ML 호환 multi-array) × N프레임 윈도우, 통상 45~90프레임
- 출력: forehand / backhand / serve / volley / none
- Mac에서 학습 → Core ML로 온디바이스 추론
- Apple 공식 경로라 툴체인이 안정적

**교체 경로**: 정확도 90% 미달 시 커스텀 1D-CNN / GRU로 전환. 수집 데이터는 그대로 재사용되므로 비용은 학습 파이프라인 구축에 한정된다.

**학습 데이터 확보 계획**
1. 자체 촬영 (본인 + 지인) — 유형별 최소 200회씩
2. 좌우 반전 / 시간 신축 / 노이즈 주입으로 증강
3. 공개 데이터셋 검토 (THETIS, Tenniset 등)
4. 앱 출시 후 사용자 데이터 수집 (옵트인) → 재학습 루프

### 페이즈 분할

스윙 구간을 5단계로 나눕니다.

| 페이즈 | 검출 기준 |
|---|---|
| 준비 (Ready) | 손목 속도 최소, 자세 안정 |
| 테이크백 (Takeback) | 손목이 뒤로 이동, 어깨 회전 시작 |
| 포워드스윙 (Forward) | 손목 속도 급증, 방향 전환점 |
| **임팩트 (Impact)** | 손목 속도 최대점 ± 공 궤적 시작점 |
| 팔로스루 (Follow-through) | 속도 감소, 손목이 반대편 어깨 방향 |

**임팩트 프레임 특정이 가장 중요합니다.** 대부분의 교정 지표가 이 프레임 기준으로 계산되기 때문입니다. 공 궤적 검출이 성공하면 궤적의 시작 시점과 교차 검증해 정확도를 크게 높일 수 있습니다.

## 3.4 공 궤적 추적

### 문제의 본질

테니스 공은 컴퓨터 비전에서 최악의 조건을 모두 갖췄습니다.
- 화면 내 **10~20px** (일반 object detector의 최소 검출 크기 근처)
- 시속 100km 이상 → 60fps에서 프레임당 **수십 px 이동**, 심한 모션 블러
- 배경과 색이 겹칠 수 있음 (연두색 공 / 초록 코트, 흰 공 / 흰 라인)
- 프레임 아웃, 라켓·신체에 의한 가림

### 온디바이스 접근

✅ **확정(온디바이스)** — Apple Vision `DetectTrajectoriesRequest` (신규 Swift API). [D-06](../05-결정/stack/D-06-pose-engine.md)과 같은 근거 — 의존성 0, ANE 가속. **Phase 0 게이트의 검증 대상**이다

**이 API는 정확히 이 문제를 위해 만들어졌습니다.** 일반 object detection이 아니라, 연속 프레임에서 **포물선 궤적을 그리는 움직임**을 직접 찾습니다. Apple의 WWDC20 *Action & Vision* 샘플 앱이 그대로 레퍼런스입니다 (빈백 던지기 궤적 + 자세 분석 — TeniTeni와 문제 구조가 동일).

주요 파라미터:
| 파라미터 | 의미 | 튜닝 방향 |
|---|---|---|
| `trajectoryLength` | 궤적 확정에 필요한 최소 검출 점 수 (최소 5) | **5**로 시작 — Phase 0은 검출 상한을 재야 하므로 관대하게 |
| `frameAnalysisSpacing` | 분석 프레임 간격 | 0으로 두면 전 프레임 분석 |
| `targetFrameTime` | 목표 프레임 처리 시간 | 성능 예산에 맞춰 조절 |
| `objectMinimumNormalizedRadius` | 검출 대상 최소 크기 | **0.002** — [촬영 프로토콜 5.4](CAPTURE-PROTOCOL.md#54-궤적-검출-파라미터-초기값) |
| `objectMaximumNormalizedRadius` | 최대 크기 | **0.015** — 모션 블러 여유 포함 |

**결정적 제약: 카메라가 고정되어야 합니다.** 프레임 간 배경 움직임을 노이즈로 처리하는 구조라, 손으로 들고 찍으면 검출이 완전히 무너집니다.

→ 이 제약은 기술적 한계가 아니라 **UX 요구사항으로 승격**시켜야 합니다 (구체 스펙은 [촬영 프로토콜 5.6](CAPTURE-PROTOCOL.md#56-프레이밍-가이드-앱-ui)):
- 온보딩에서 삼각대 사용을 명시적으로 안내
- 촬영 화면에 프레이밍 가이드 오버레이
- 가속도계로 흔들림 감지 → 실시간 경고
- 흔들림이 심하면 궤적 기능을 자동 비활성화하고 이유를 알림

### 서버 접근 (고정밀)

⏸ **보류** — [D-20](../05-결정/stack/D-20-server-ml.md). Phase 0에서 온디바이스 검출률이 70%를 넘으면 도입 명분이 크게 줄어든다. 후보:

| 후보 | 방식 | 비고 |
|---|---|---|
| **TrackNetV2 / V3** | 연속 3프레임 → 히트맵. 소형 고속 물체 전용 설계 | 테니스/배드민턴 논문의 표준. 가장 유력 |
| YOLOv8/v11 + ByteTrack | 검출 + 추적 분리 | 작은 물체에 약함. 타일링 필요 |
| 배경 차분 + 칼만 필터 | 고전적 CV | 고정 카메라에서 의외로 강력. 비용 0 |

후처리는 공통입니다: 칼만 필터로 결측 보간 → 물리 모델(포물선 + 공기저항) 피팅 → 이상치 제거.

### 코트 인식과 좌표 변환

⏸ **Phase 3 과제** — [D-20](../05-결정/stack/D-20-server-ml.md) 판정과 함께 결정

1. 코트 라인 검출 (Hough 변환 또는 학습 기반 세그멘테이션)
2. 표준 코트 규격(23.77m × 8.23m 단식)과 대응점 매칭
3. 호모그래피 행렬 산출
4. 영상 좌표 궤적 → 코트 평면 좌표로 투영
5. 바운스 지점 추정 (궤적의 y축 방향 전환점) → 인/아웃 판정, 구속 추정

조명 변화와 부분 가림에 취약하므로, 세션 시작 시 **1회 캘리브레이션**한 뒤 고정하는 방식이 현실적입니다.

## 3.5 메트릭 산출

임팩트 프레임과 페이즈 경계를 기준으로 계산합니다.

| 메트릭 | 정의 | 관련 페이즈 |
|---|---|---|
| `kneeFlexion` | 무릎 굴곡 각 (엉덩이-무릎-발목) | 준비, 임팩트 |
| `hipShoulderSeparation` | 골반선과 어깨선의 각도 차 (X-Factor) | 테이크백 최대 |
| `elbowAngleAtImpact` | 어깨-팔꿈치-손목 각 | 임팩트 |
| `contactPointHeight` | 임팩트 시 손목 높이 (어깨 기준 정규화) | 임팩트 |
| `contactPointDepth` | 임팩트 시 손목의 전후 위치 (골반 기준) | 임팩트 |
| `shoulderTilt` | 어깨선 기울기 | 전 구간 |
| `headStability` | 코 관절의 위치 분산 | 전 구간 |
| `followThroughAngle` | 팔로스루 종료 시 손목-어깨 각 | 팔로스루 |
| `weightTransfer` | 발목 중점 대비 골반 수평 이동량 | 전 구간 |

모든 각도는 **신장 및 어깨너비로 정규화**해 체격 차이를 제거합니다.

## 3.6 자세 평가 — 가장 어려운 문제

### 왜 ML로 풀면 안 되는가

"이 스윙은 87점"을 출력하는 모델을 만들려면 **점수가 라벨링된 스윙 데이터셋**이 필요합니다. 그런 데이터셋은 존재하지 않고, 만들려면 코치 수십 명이 수천 개 영상을 채점해야 합니다. 개인 프로젝트에서 가능한 일이 아닙니다.

더 근본적으로, 프로 선수들의 폼은 서로 크게 다릅니다. 정답이 하나가 아닙니다.

### 채택 방향: 3단계 점진적 접근

✅ **확정** — 룰 엔진 우선, 학습형은 데이터가 쌓인 뒤

**1단계 — 룰 기반 (Phase 1)**
- 코칭 문헌과 코치 자문으로 각 메트릭의 권장 범위를 정의
- 범위 이탈 시 심각도와 함께 피드백 생성
- 예: `elbowAngleAtImpact`가 112° → 권장 150~170° 이탈 → "임팩트 시 팔꿈치가 과도하게 굽혀져 있습니다"
- 장점: 설명 가능, 데이터 불필요, 즉시 구현 가능
- **한 스윙에 최대 2~3개 피드백만** 노출. 5개 띄우면 아무도 안 읽습니다

**2단계 — 레퍼런스 비교 (Phase 2~3)**
- 프로 선수 스윙 시퀀스를 레퍼런스로 저장
- 체격 정규화 후 **DTW(Dynamic Time Warping)** 로 시간축 정렬
- 구간별 편차가 큰 지점을 시각적으로 강조
- 리플레이에 레퍼런스 스켈레톤을 반투명 고스트로 겹쳐 표시 → **킬러 기능**

**3단계 — 학습형 (Phase 4+)**
- 사용자 데이터와 코치 피드백이 축적된 뒤에만 착수
- 그 전까지는 착수하지 않는다

### 피드백 설계 원칙

- **한 번에 하나**를 고치게 한다. 우선순위가 가장 높은 문제 1개를 크게 보여준다
- **원인이 아니라 동작**을 지시한다. "체중 이동이 부족합니다"(❌) → "앞발에 체중을 더 실어보세요"(⭕)
- **수치를 함께 보여준다**. 신뢰도가 올라가고, 다음 촬영에서 개선을 확인할 수 있다
- **틀릴 수 있음을 인정한다**. 신뢰도가 낮으면 단정하지 않는다

## 3.7 성능 예산

60fps 기준 프레임당 예산은 **16.6ms**입니다.

| 작업 | 예상 비용 (A17 기준) | 비고 |
|---|---|---|
| 다운스케일 640×360 | ~0.5ms | vImage / Metal |
| 포즈 추정 | 3~5ms | 640×360 입력 기준 |
| 궤적 검출 | 2~4ms | `frameAnalysisSpacing`으로 조절 |
| 스무딩 + 각도 계산 | <0.5ms | |
| 스윙 분류 | ~2ms | 윈도우 단위이므로 매 프레임 아님 |
| 오버레이 렌더 | 1~2ms | 관절 19개는 가벼움 |
| **합계** | **~10~14ms** | 여유 있으나 발열 시 여유가 줄어듦 |

> **120fps를 선택하면 예산이 8.3ms로 반토막**입니다. 이때는 [D-04](../05-결정/stack/D-04-concurrency.md)의 스트림 분리로 **궤적만 전 프레임, 포즈는 60fps로 데시메이션**합니다. 사람 동작은 120Hz 샘플링이 필요 없고 공은 필요합니다.

**최적화 원칙**
- 분석 입력은 반드시 다운스케일한다. 1080p 원본을 그대로 넣지 않는다
- **노출을 짧게 고정한다.** 자동 노출이면 모션 블러로 공이 뭉개져 검출 자체가 불가능하다 ([촬영 프로토콜 5.3](CAPTURE-PROTOCOL.md#53-노출--이것이-궤적-검출을-좌우한다))
- 3D 포즈, 서버급 모델은 실시간 경로에 넣지 않는다
- 발열 감지(`ProcessInfo.thermalState`) 시 `frameAnalysisSpacing`을 동적으로 늘려 품질을 낮춘다
- 240fps 촬영은 **저장 용량이 분당 500MB**를 넘으므로 스윙 구간에만 적용한다
