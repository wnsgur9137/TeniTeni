# ADR-0002. 모노레포 채택

- **상태**: Proposed
- **날짜**: 2026-09-10

## 맥락

iOS 앱, 백엔드 API, ML 학습 코드, API 스펙을 어떻게 저장소로 나눌지 결정해야 합니다.

제약 조건:
- 현재 개발 인원 1명
- iOS와 서버가 API 스펙을 공유한다
- ML 모델 변경이 iOS(Core ML)와 서버(PyTorch) 양쪽에 동시 영향을 준다
- 모델 파일과 샘플 영상이라는 대용량 바이너리가 있다

## 검토한 선택지

### A. 멀티레포 (`teniteni-ios`, `teniteni-server`, `teniteni-ml`, `teniteni-contracts`)
- ✅ 저장소별 CI가 가볍다, 권한 분리가 명확하다
- ✅ 컴포넌트별 릴리즈 주기가 독립적이다
- ❌ API 스펙 변경 시 **여러 PR을 조율**해야 한다. 1인 개발에서 순수 오버헤드
- ❌ 이슈/보드/릴리즈 노트가 4곳으로 흩어진다
- ❌ 크로스 컴포넌트 변경의 원자성이 깨진다

### B. 모노레포 (`TeniTeni` 단일)
- ✅ API 계약 변경을 **한 PR에서 원자적으로** 처리
- ✅ 이슈·보드·문서가 한 곳
- ✅ 로컬 개발 환경 부트스트랩이 단순 (`make bootstrap` 하나)
- ❌ CI가 전체를 돌면 느리다
- ❌ 저장소 크기가 커진다
- ❌ 나중에 분리하려면 히스토리 처리가 번거롭다

## 결정

**B. 모노레포를 채택한다.**

비용은 다음으로 완화합니다:
- GitHub Actions `paths` 필터로 변경 영역만 CI 실행
- Git LFS로 모델/샘플 영상 분리, 학습 데이터셋은 DVC 포인터만 커밋
- 컴포넌트별 태그 프리픽스 (`ios-v*`, `server-v*`, `model-v*`)

## 결과

**쉬워지는 것**
- `contracts/openapi.yaml` 변경 → 서버 구현 → iOS 클라이언트 재생성이 한 PR에서 끝난다
- CI에서 계약 불일치를 PR 단계에 차단할 수 있다

**어려워지는 것**
- CI 설정이 조금 더 복잡하다 (paths 필터, 캐시 분리)
- Git LFS를 **초기에 반드시** 설정해야 한다. 나중에 걸면 히스토리 재작성이 필요하다

**분리 시점**: 팀이 3명 이상이 되고 iOS와 서버의 릴리즈 주기가 완전히 갈라질 때. 그 전에 쪼개는 것은 손해다.

**되돌리는 비용**: 낮음~중간. `git filter-repo`로 서브디렉터리를 별도 저장소로 추출할 수 있다.
