# ADR-0004. 촬영 모드 분리와 실시간 라인 판정

- **상태**: Accepted
- **날짜**: 2026-09-14
- **이슈**: [#44](https://github.com/wnsgur9137/TeniTeni/issues/44)

## 맥락

인/아웃 판정을 **촬영 중 실시간으로 화면에 표시**하기로 했습니다. 기존 문서는 이것을 Phase 3의 서버 사후 분석으로 다뤘습니다 ([제품 개요](../../01-제품/PRODUCT-OVERVIEW.md) UC-3, [비전 파이프라인](../../02-설계/VISION-PIPELINE.md) 3.1·3.4).

기능 정의가 바뀌면서 두 가지가 드러났습니다.

### 1. 두 기능이 요구하는 카메라 배치가 정반대다

[촬영 프로토콜 5.1](../../02-설계/CAPTURE-PROTOCOL.md)은 **측면 6m, 높이 1.1m**입니다. 선수를 담도록 설계된 배치입니다.

라인 판정은 다릅니다. 지면 위 한 점의 측정 정밀도가 방향에 따라 크게 갈리기 때문입니다.

| 방향 | 1px당 지면 거리 | 비례 |
|---|---|---|
| 깊이 (카메라에서 멀어지는 쪽) | `Δθ · d² / h` | 거리의 **제곱** |
| 가로 (화면을 가로지르는 쪽) | `Δθ · d` | 거리에 **비례** |

수평 화각 70°·1080p·카메라 높이 1.1m로 계산하면:

| 거리 | 깊이 방향 | 가로 방향 | 비 |
|---|---|---|---|
| 11 m | 7.7 cm | **0.76 cm** | 10× |
| 20 m | 25.3 cm | **1.39 cm** | 18× |

**라인 폭은 5 cm입니다.** 현재 측면 배치로는 12 m에서 이미 1픽셀이 라인보다 넓어 판정이 불가능합니다.

> 화각 70°는 계산 가정입니다. [#4](https://github.com/wnsgur9137/TeniTeni/issues/4)의 실측으로 보정합니다. 비율 관계는 화각과 무관하게 성립합니다.

프레이밍도 맞지 않습니다. 6 m에서 프레임 폭이 8.4 m인데 한쪽 코트만 11.89 m입니다 — **71%만 담깁니다.** 인/아웃이 갈리는 상대 코트 베이스라인은 프레임 밖입니다.

### 2. 실시간이 오히려 쉽다

삼각대 고정이 전제이므로 **코트가 움직이지 않습니다.** 호모그래피를 세션 시작 때 한 번만 구하면 이후 매 프레임은 3×3 행렬 곱 한 번이라 120fps 예산(8.3 ms)에 들어갑니다.

[비전 파이프라인 3.4](../../02-설계/VISION-PIPELINE.md)가 이미 "세션 시작 시 1회 캘리브레이션한 뒤 고정하는 방식이 현실적"이라고 적었습니다.

지연은 약 **50~60 ms**입니다.

| 단계 | 시간 |
|---|---|
| 바운스로 끊긴 포물선 재확정 (`trajectoryLength` 5프레임 @ 120fps) | 42 ms |
| Vision 요청 지연 | 3~15 ms |

서버를 거치지 않으므로 네트워크 왕복이 없습니다.

## 검토한 선택지

### 배치

| 선택지 | 장점 | 단점 |
|---|---|---|
| A. 한 배치로 둘 다 | 사용자가 폰을 옮기지 않는다 | **기하적으로 불가능.** 위 표 참조 |
| **B. 모드를 나눈다** | 각 기능이 최적 배치를 쓴다 | 모드 전환 시 폰을 옮겨야 한다 |
| C. 라인 판정 포기 | 단순 | 제품 정의([제품 개요](../../01-제품/PRODUCT-OVERVIEW.md) 1.1)의 절반을 버린다 |

**채택: B.**

### 캘리브레이션

| 선택지 | 장점 | 단점 |
|---|---|---|
| **A. 정지 프레임 4점 수동 탭** | 견고하다. 실패해도 원인이 명확하다. 세션당 10초 | 사용자 손이 간다 |
| B. 자동 라인 검출 (Hough·세그멘테이션) | 손이 안 간다 | **조명 변화·부분 가림에 취약** — 비전 파이프라인 3.1이 이미 경고 |
| C. 자동 + 수동 보정 | UX가 가장 좋다 | 구현이 두 배. A가 동작해야 C도 의미가 있다 |

**채택: A.** C는 A가 자리 잡은 뒤 검토합니다.

### 담당 레인

[ADR-0001](ADR-0001-hybrid-inference.md)이 이미 정했습니다.

> 실시간 레인(온디바이스): **촬영 중 오버레이**, 스윙 검출, 즉시 피드백

**실시간 인/아웃은 정의상 실시간 레인입니다.** 비전 파이프라인 3.1의 "담당: 서버"는 인/아웃을 사후 분석으로 전제했기 때문이며, 기능 정의가 바뀌니 레인이 바뀝니다. **ADR-0001을 뒤집지 않습니다.**

## 결정

**촬영을 두 모드로 나누고, 라인 판정을 실시간 온디바이스로 둔다.**

| | 스윙 분석 모드 | 라인 판정 모드 |
|---|---|---|
| 배치 | 측면, 코트 장축에 수직 | **판정할 라인의 연장선** |
| 거리·높이 | 6 m · 1.1 m | 라인이 화면을 가로지르게 |
| 담는 것 | 선수 (프레임 높이 35~45%) | 라인 + 여유 |
| 캘리브레이션 | 없음 | **4점 수동 탭** (세션 1회) |
| 산출 | 스켈레톤·관절 각도·피드백 | 바운스 위치·인/아웃 |
| 페이즈 | Phase 0~1 | **Phase 1 후반 (1-F)** |

### 판정은 3분류로 낸다

**"명백한 인 / 명백한 아웃 / 판정 불가".** 2분류로 내지 않습니다.

이유는 **정확도를 검증할 방법이 없기 때문**입니다. Hawk-Eye는 공인 오차(약 3.6 mm, 카메라 10대 이상 / 340 fps)가 있지만 우리에게는 정답이 없습니다. 클레이 코트의 바운스 자국을 자로 재거나 기준 카메라를 따로 두는 수밖에 없고, 이는 [Phase 0 게이트](../../02-설계/CAPTURE-PROTOCOL.md)와 같은 성격의 문제입니다 — 사람이 실측해야 합니다.

검증 없이 "아웃"을 단정하면 사용자가 그것을 근거로 다투게 되고, 틀렸을 때 제품 신뢰가 무너집니다. **판정 불가 밴드를 넉넉히 두는 쪽**이 제품 수명에 유리합니다.

## 결과

**쉬워지는 것**

- 각 모드가 자기 배치를 쓰므로 타협이 없다
- 삼각대 고정 덕분에 호모그래피가 세션당 1회 — 실시간 예산에 여유가 있다
- 오프라인에서 동작한다 (ADR-0001의 오프라인 우선 원칙과 일치)

**어려워지는 것**

- **모드 전환 시 사용자가 폰을 옮겨야 한다.** 안내 UI가 필요하다 — [촬영 프로토콜 5.6](../../02-설계/CAPTURE-PROTOCOL.md)의 프레이밍 가이드를 모드별로 나눈다
- **한 번에 한 라인만 판정한다.** 카메라 1대의 한계이며, 어느 라인을 볼지 사용자가 고른다
- 캘리브레이션이 틀리면 판정이 통째로 틀린다 → 캘리브레이션 직후 **검증 화면**(코트 격자를 영상에 겹쳐 보여주기)이 필요하다

**되돌리는 비용**: 낮음. 모드 분리는 UI 층의 분기이고, 라인 판정을 빼도 스윙 분석 경로는 그대로다.

## 미해결

- **정확도 실측** — 실기기와 실제 코트가 있어야 한다. [#4](https://github.com/wnsgur9137/TeniTeni/issues/4) 이후
- **판정 불가 밴드의 폭** — 위 실측 없이 정할 수 없다. 잠정적으로 넓게 두고 좁혀 나간다
- **Phase 0 게이트 선행** — 궤적을 못 잡으면 바운스도 못 잡는다
