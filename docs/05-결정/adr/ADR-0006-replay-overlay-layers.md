# ADR-0006. 오버레이는 촬영 중이 아니라 리플레이에서 그린다

- **상태**: Accepted
- **날짜**: 2026-10-27
- **이슈**: [#121](https://github.com/wnsgur9137/TeniTeni/issues/121)
- **대체하는 결정**: [D-07 오버레이 렌더링](../stack/D-07-overlay-rendering.md)

## 맥락

[D-07](../stack/D-07-overlay-rendering.md)은 "처음부터 Metal로 프리뷰를 직접 렌더한다. `AVCaptureVideoPreviewLayer`를 쓰지 않는다"로 확정됐습니다. 그 결정의 **근거는 전부 실시간 지연**이었습니다.

> 프리뷰 레이어 위에 겹치는 방식은 구조적으로 1~3프레임 늦고, 초당 30m로 움직이는 테니스 스윙에서는 팔이 스켈레톤 밖으로 튀어나간다. 속도 외삽은 임시방편일 뿐이다.

[스켈레톤 오버레이 4.2](../../02-설계/SKELETON-OVERLAY.md)는 절 하나를 통째로 이 문제에 썼고, 해법은 "영상 표시를 추론 결과에 맞춰 지연시킨다"였습니다 — 화면 전체를 3~15ms 늦춰 영상과 오버레이를 같은 시각에 맞추는 방식입니다.

**그런데 오버레이를 촬영 중에 보여주지 않기로 했습니다.** 사용자가 리플레이에서 골라 켭니다. 그러면 위 근거가 전부 사라집니다 — 리플레이는 파일 재생이고, 프레임과 오버레이 데이터를 **임의로 맞춰 둘 수 있습니다.**

근거가 사라진 결정을 그대로 두면 다음 사람이 "왜 Metal인가"를 읽고 틀린 전제를 이어받습니다.

## 검토한 선택지

### 1. D-07을 유지하고 리플레이도 Metal로 그린다

렌더 경로가 하나로 유지되고, [4.8 녹화 영상 합성](../../02-설계/SKELETON-OVERLAY.md)(오프스크린 텍스처 → `AVAssetWriter`)이 그대로 재사용됩니다. D-07의 **두 번째 근거는 여전히 유효합니다.**

그런데 지금 그 합성 기능이 없습니다. 쓰지 않는 기능을 위해 구현 비용이 큰 경로를 먼저 깔게 됩니다. 그리고 리플레이는 슬로우 모션(0.25×)이 기본이라 초당 15~30프레임만 그리면 됩니다 — Metal이 해결하는 문제가 하나도 남지 않은 자리입니다.

### 2. 리플레이는 SwiftUI Canvas, 라이브 프리뷰는 `AVCaptureVideoPreviewLayer`

D-07이 "단계적 전환은 결국 두 번 작업하는 것"이라고 거부한 Canvas가 **중간 단계가 아니라 종착지**가 됩니다. 그 근거가 뒤집힙니다.

라이브는 이미 `AVCaptureVideoPreviewLayer`로 돌고 있습니다([#82](https://github.com/wnsgur9137/TeniTeni/issues/82)에서 회전각까지 맞췄습니다). 오버레이가 없으면 그것으로 충분합니다.

### 3. 라이브 오버레이를 선택 기능으로 남긴다

"코트에서도 보고 싶다"를 열어둡니다. 그러나 [IA-FLOW 10.5](../../06-디자인/IA-FLOW.md)가 정한 6m 가독성 원칙과 충돌합니다 — 6m 밖에서 스켈레톤의 **세부**는 읽히지 않고, 읽으려 다가오면 촬영이 끊깁니다. 그리고 D-07의 지연 문제가 다시 살아나 Metal이 필요해집니다.

## 결정

**선택지 2를 채택합니다.**

| 경로 | 렌더 | 오버레이 |
|---|---|---|
| **촬영 중** | `AVCaptureVideoPreviewLayer` | **없음** |
| **리플레이** | SwiftUI Canvas (영상은 `AVPlayerLayer`) | 레이어 **하나**를 골라 켠다 |

### 촬영 중 "잡히고 있나"는 스켈레톤이 아니라 상태 표시로 답한다

IA-FLOW 10.5의 1층(6m용) 표에 인식 상태가 **"스켈레톤 오버레이 자체"**로 적혀 있었습니다. 그것이 사라지므로 대체가 필요합니다.

대체는 이미 코드에 있습니다 — `CameraController.PoseIndicator`(`idle` / `detected` / `notFound` / `unusable` / `failed` / `unavailable`). 문서가 코드보다 뒤처져 있었고, 이 결정이 그것을 정본으로 올립니다.

**이것이 오히려 6m 원칙에 맞습니다.** 스켈레톤은 "사람 형태가 보이면 OK"라는 간접 신호였고, 상태 표시는 직접 답입니다. 특히 `unusable`("사람은 보이는데 어깨를 못 믿는다 — 측면으로 서면 이렇게 된다")은 스켈레톤을 봐서는 알 수 없는 것입니다.

### 레이어는 한 번에 하나만 켠다

독립 토글 4개는 조합 16가지이고 대부분은 시각적 소음입니다. [PadelRadar](https://apps.apple.com/app/id6786744940)가 배타적 모드 5개(공 트레일만 / 공 속도만 / 플레이어 속도 / 포즈 / 전체)로 가는 것과 같은 판단입니다.

리플레이는 **폰 앞에서 보는 화면**이므로 탭 한 번의 비용이 작습니다 — 6m 제약을 받는 촬영 화면과 다릅니다.

### 오버레이 데이터는 클립 저장 직후 한 번 굽는다

리플레이를 열 때 계산하면 열 때마다 기다리고 배터리를 또 씁니다. 결과는 클립당 결정적이므로 한 번 계산해 사이드카에 둡니다.

```
녹화 종료 → 클립 .mov 저장
            ↓ 백그라운드 1회
    AVAssetReader로 순차 읽기 (CMSampleBuffer 유지)
      ├─ DetectHumanBodyPoseRequest(detectsHands)
      └─ DetectTrajectoriesRequest            ← 0-C 게이트 통과 시
            ↓
    사이드카 (프레임별 관절 + 궤적 점 + 신뢰도)
```

`CGImage`로 변환하면 타임스탬프가 사라져 `timeRange`가 `nil`이 됩니다 — `teni analyze`가 이미 겪은 함정입니다([DetectTrajectories 4절](../../08-레퍼런스/ml/DetectTrajectories.md)).

## 결과

### 좋아지는 것

- **측정되지 않은 위험 하나가 없어집니다.** `DetectTrajectories.md` 5절이 "`minimumLatencyFrameCount` 실측 — 0-D 지연 예산에 필요하다. **오프라인에서는 문제가 없어 재지 않았다**"로 남겨둔 항목입니다. 궤적이 오프라인이면 그 미지수가 사라집니다
- **0-C 게이트 미달의 타격이 작아집니다.** [WORK-PLAN 9.8](../../04-계획/WORK-PLAN.md)의 조치는 "궤적 기능 v1 제외"인데, 빠지는 것이 실시간 렌더 경로가 아니라 **리플레이 레이어 하나**입니다
- **실시간 프레임 예산이 줄어듭니다.** 라이브에 남는 분석은 스윙 트리거용 포즈 하나입니다
- [D-04](../stack/D-04-concurrency.md)가 적은 "궤적 검출과 오버레이는 요구가 정반대다"라는 대립이 **없어집니다.** 궤적은 연속 프레임이 필요하고 오버레이는 최신 프레임이 필요했는데, 둘 다 오프라인이면 연속 프레임만 있으면 됩니다

### 나빠지는 것 · 포기하는 것

- **코트에서 포즈가 잡히는지 눈으로 확인할 수 없습니다.** `PoseIndicator`를 믿어야 합니다
- **오버레이를 구운 영상 내보내기가 멀어집니다.** Canvas로는 D-07의 4.8 경로를 쓸 수 없습니다. 그 기능이 필요해지면 **그때 Metal 렌더러를 따로 만듭니다** — D-07이 피하려던 "두 번 작업"이 이 지점에서는 발생합니다. 지금 없는 기능을 위해 큰 비용을 먼저 치르지 않는 쪽을 택했습니다
- **클립 저장 후 사이드카가 구워지기까지 리플레이에 오버레이가 없습니다.** 그 사이의 화면 상태를 설계해야 합니다

### `RenderTransform`은 그대로 쓴다

[SPEC-0040](../../07-기획/SPEC-0040-render-transform.md)의 행렬은 **각도를 인자로 받는** 순수 함수입니다. 입력이 라이브 버퍼에서 파일 프레임으로 바뀌어도 수학이 같습니다.

달라지는 것은 각의 **출처**입니다 — 라이브는 `RotationCoordinator`, 리플레이는 비디오 트랙의 `preferredTransform`입니다. [#82](https://github.com/wnsgur9137/TeniTeni/issues/82)가 녹화 커넥션에 `videoRotationAngle`을 심어 두었으므로 그 값이 파일에 들어 있습니다.

## 미해결

- **라켓 헤드 추정의 정확도를 판정할 방법이 없습니다.** 정답이 없으므로 "그럴듯한가"까지만 봅니다. 한계는 [SPEC-0121](../../07-기획/SPEC-0121-replay-overlay.md)에 적었습니다
- **라인 레이어는 1-F 호모그래피가 선행입니다.** 볼 궤적은 0-C 게이트가 선행입니다. 네 레이어 중 둘은 지금 만들 수 없습니다
- 사이드카를 **어디에 둘지**(파일 vs SwiftData)는 SPEC에서 정합니다
- 오버레이를 구운 영상 내보내기를 언제 할지 정하지 않았습니다
