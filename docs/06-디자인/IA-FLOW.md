# 10. 정보 구조와 화면 흐름

## 10.1 이 앱의 UX를 지배하는 제약

사용자는 **코트에 있고, 폰은 6m 떨어진 삼각대에 있고, 손에는 라켓이 있습니다.**

```
스윙 → (폰까지 걸어감) → 확인 → (돌아감) → 스윙
```

이 왕복 비용이 모든 설계를 결정합니다. 일반 모바일 앱처럼 "화면을 보며 조작한다"는 전제가 성립하지 않습니다.

### 따라 나오는 원칙

| 원칙 | 이유 |
|---|---|
| **촬영 중 UI는 6m 밖에서 읽혀야 한다** | 세밀한 정보는 무의미. 큰 숫자와 색상만 |
| **소리가 화면보다 중요하다** | 스윙 감지음이 있으면 폰을 안 봐도 인식 여부를 안다 |
| **피드백의 주 무대는 리플레이** | 폰 앞에 왔을 때 비로소 자세히 본다 |
| **조작은 촬영 전후에 몰아넣는다** | 촬영 중 설정 변경은 불가능하다고 봐야 한다 |

> [D-07](../05-결정/stack/D-07-overlay-rendering.md)에서 Metal 직접 렌더로 지연을 없앴지만, 그 정밀함을 **촬영 중에 볼 사람이 없습니다.** 실시간 오버레이의 진짜 용도는 "제대로 잡히고 있다"는 확인이고, 정밀한 판정은 리플레이에서 합니다. [스켈레톤 오버레이 4.2](../02-설계/SKELETON-OVERLAY.md)의 설계 원칙과 일치합니다.

## 10.2 화면 목록

[WORK-PLAN 9.6](../04-계획/WORK-PLAN.md)의 `Presentation` 모듈 6개에 대응합니다.

| # | 화면 | 모듈 | 역할 | 사용 시점 |
|---|---|---|---|---|
| 1 | **온보딩** | `Onboarding` | 카메라 배치 안내, 권한, 프로필 | 최초 1회 |
| 2 | **촬영** | `Capture` | **모드 선택** → 프레이밍 → 촬영 → 실시간 오버레이 | 코트에서 |
| 3 | **세션 요약** | `Session` | 방금 친 세션의 스윙 목록·분포·점수 | 촬영 직후 |
| 4 | **스윙 리플레이** | `Analysis` | 슬로우 모션 + 스켈레톤 + 페이즈 + **피드백** | ★ 핵심 |
| 5 | **보관함** | `Library` | 과거 세션·클립 탐색 | 집에서 |
| 6 | **진척도** | `Progress` | 기간별 지표 추이 | 주 단위 |

**4번이 이 앱의 심장입니다.** 나머지는 4번으로 가는 경로이거나 4번의 집계입니다.

## 10.3 주 흐름

```
[온보딩] ─최초 1회─┐
                   ▼
              ┌─────────┐
              │  홈/촬영 │◄──────────────┐
              └────┬────┘               │
                   │ 촬영 시작           │
                   ▼                    │
         ┌──────────────────┐           │
         │   촬영 중         │           │
         │  (6m 밖 가독성)   │           │
         │  스윙 감지음 ♪    │           │
         └────────┬─────────┘           │
                  │ 종료                 │
                  ▼                     │
           ┌─────────────┐              │
           │  세션 요약   │──이어서 촬영──┘
           └──────┬──────┘
                  │ 스윙 선택
                  ▼
           ┌─────────────┐
           │ 스윙 리플레이 │  ★ 피드백이 여기 있다
           └─────────────┘

[보관함] ──→ 세션 요약 ──→ 스윙 리플레이   (같은 목적지)
[진척도] ──→ 특정 스윙 ──→ 스윙 리플레이
```

**모든 경로가 리플레이로 수렴합니다.** 보관함과 진척도는 별도 목적지가 아니라 리플레이로 가는 다른 입구입니다.

## 10.4 촬영 모드

✅ **확정** — 세 모드를 모두 지원하고 **사용자가 선택**한다.

모드가 바꾸는 것은 **폰까지의 왕복 빈도**이고, 그에 따라 촬영 화면과 피드백 시점이 달라진다.

| 모드 | 상황 | 왕복 빈도 | 촬영 화면 설계 |
|---|---|---|---|
| **연속** | 볼머신 · 벽치기 | 거의 없음 | 소리 피드백 최대화, 화면은 카운트만. 세션이 길다 |
| **랠리** | 상대와 경기 | 중간 (체인지·휴식) | **세션 중간 확인 화면** 필요. 직전 스윙 빠르게 보기 |
| **레슨** | 코치 동석 | 잦음 | 즉석 리플레이·비교가 주. 자동 피드백 비중 낮음 |

모드는 촬영 시작 전에 고르고, 세션 메타에 기록한다. 세션 간 비교 시 모드가 다르면 나란히 놓지 않는다 — 스윙 밀도와 조건이 다르다.

### 모드별 차이 요약

| | 연속 | 랠리 | 레슨 |
|---|---|---|---|
| 스윙 감지음 | ✅ 필수 | ✅ | 선택 (코치 방해) |
| 중간 확인 화면 | ✗ | ✅ | ✅ |
| 세션 예상 길이 | 길다 | 중간 | 짧다 |
| 자동 피드백 노출 | 세션 후 | 중간·세션 후 | 최소 |

## 10.5 촬영 중 화면 — 6m 가독성

세밀한 정보를 버리고 **세 가지만** 남깁니다.

| 요소 | 표현 | 6m에서 읽히는가 |
|---|---|---|
| 인식 상태 | 스켈레톤 오버레이 자체 | ✅ 사람 형태가 보이면 OK |
| 스윙 카운트 | **초대형 숫자** | ✅ |
| 이상 상태 | 화면 테두리 색 (정상=없음 / 경고=주황 / 오류=빨강) | ✅ |

수치·설정·피드백은 촬영 중에 표시하지 않습니다. 읽을 수 없고, 읽으려 다가오면 촬영이 끊깁니다.

### 소리 설계

화면보다 중요합니다.

| 이벤트 | 소리 |
|---|---|
| 스윙 감지 | 짧은 톤 1회 — "잡혔다" |
| 인식 실패(프레임 이탈 등) | 낮은 톤 — "다시" |
| 흔들림·발열 경고 | 경고음 + 테두리 색 |
| 녹화 시작/종료 | 구분되는 톤 |

**스윙 감지음만 있어도 폰을 안 봐도 됩니다.** 이게 왕복 횟수를 줄이는 가장 큰 장치입니다.

## 10.6 스윙 리플레이 — 피드백을 어떻게 보여줄 것인가

[ADR-0003](../05-결정/adr/ADR-0003-rule-based-evaluation.md)이 원칙을 정했습니다. 그걸 화면으로 옮깁니다.

| ADR 원칙 | 화면 구현 |
|---|---|
| 한 번에 하나를 고치게 한다 | **피드백 1개를 크게**, 나머지는 접어둔다 |
| 원인이 아니라 동작을 지시한다 | "앞발에 체중을 더 실어보세요" (❌ "체중 이동 부족") |
| 수치를 함께 보여준다 | 지시 아래 작게 `112° · 권장 150~170°` |
| 틀릴 수 있음을 인정한다 | **신뢰도로 표현을 나눈다 (아래)** |

### ✅ 톤 — 신뢰도로 구분한다

확정 사항이다. 하나의 톤으로 통일하지 않는다.

| 신뢰도 | 표현 | 예 |
|---|---|---|
| **높음** — 룰 임계를 확실히 벗어남 | **지시형** | "앞발에 체중을 더 실어보세요" |
| **낮음** — 임계 근처 · 관절 confidence 낮음 · 표본 부족 | **제시형** | "임팩트 시 팔꿈치 112°입니다. 권장 범위는 150~170°입니다" |

지시형은 초보자에게 친절하지만 틀리면 신뢰를 크게 잃습니다. 제시형은 안전하지만 초보자가 무엇을 고칠지 모릅니다. **확실할 때만 단언**하는 것이 [ADR-0003](../05-결정/adr/ADR-0003-rule-based-evaluation.md)의 "틀릴 수 있음을 인정한다"와 맞습니다.

시각적으로도 구분합니다 — 지시형은 강조 색과 큰 타이포, 제시형은 중립 색과 본문 타이포.

### 화면 구성

```
┌────────────────────────────────┐
│  영상 + 스켈레톤 (슬로우 모션)    │
│                                │
│  ◄──────●────────────────────► │  페이즈 스크러버
│  준비 테이크백 포워드 임팩트 팔로 │
├────────────────────────────────┤
│  앞발에 체중을 더 실어보세요       │  ← 지시 (크게)
│  112° · 권장 150~170°           │  ← 근거 (작게)
│                                │
│  ▸ 다른 지적 2개                 │  ← 접힘
└────────────────────────────────┘
```

**페이즈 스크러버가 핵심 인터랙션**입니다. 임팩트 프레임으로 한 번에 이동할 수 있어야 하고, 기본 재생 위치도 임팩트여야 합니다 — 대부분의 지표가 그 프레임에서 계산되기 때문입니다.

## 10.7 목업 캔버스

**소스는 저장소 안에 있습니다** — `docs/06-디자인/_canvas/`.

| 파일 | 내용 |
|---|---|
| `*.dc.html` | 아트보드 10개. 파일 하나가 화면 하나입니다 |
| `canvas.json` | 배치·주석·실행 뷰 |
| `TOKENS.txt` | 아트보드에 인라인으로 반복되는 공통 스타일 |

아트보드는 10.2의 화면 목록과 대응합니다. 세로(390×844)는 일반 화면, 가로(844×390)는 촬영·중간 확인 화면입니다 — 촬영이 landscape 고정이기 때문입니다.

### 왜 저장소에 두는가

`design` 스킬은 작업 디렉터리에 소스를 만들고, 발행된 캔버스는 편집기 코드까지 합쳐 2.4 MB가 됩니다. 소스만 두면 80 KB입니다.

**소스가 저장소 밖에 있으면 다음 작업에서 갱신할 대상을 찾지 못합니다.** 파이프라인 7단계가 "기존 캔버스가 있으면 갱신한다"고 규정하는데, 임시 디렉터리는 세션이 끝나면 사라집니다. 실제로 한 번 그렇게 될 뻔했습니다.

### 갱신·발행 절차

1. `docs/06-디자인/_canvas/`의 `.dc.html`을 고칩니다 — 새 캔버스를 만들지 않습니다
2. `design` 스킬의 `seed-canvas.mjs`로 발행 파일을 만듭니다. 아트보드와 `canvas.json`을 전부 넘깁니다
3. 발행한 뒤 **URL을 아래에 적습니다**

| 캔버스 | URL |
|---|---|
| TeniTeni 화면 10종 | *(미발행)* |

> 발행 산출물(`*.html` 2.4 MB)은 커밋하지 않습니다. 편집기 코드가 대부분이고 재생성 가능합니다.
