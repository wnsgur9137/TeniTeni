# 10. 정보 구조와 화면 흐름

## 10.1 이 앱의 UX를 지배하는 제약

사용자는 **코트에 있고, 폰은 6m 떨어진 삼각대에 있고, 손에는 라켓이 있습니다.**

```
스윙 → (폰까지 걸어감) → 확인 → (돌아감) → 스윙
```

이 왕복 비용이 모든 설계를 결정합니다. 일반 모바일 앱처럼 "화면을 보며 조작한다"는 전제가 성립하지 않습니다.

### 따라 나오는 원칙

| 원칙 | 이유 |
|---|---|
| **촬영 중 UI는 6m 밖에서 읽혀야 한다** | 세밀한 정보는 무의미. 큰 숫자와 색상만 |
| **소리가 화면보다 중요하다** | 스윙 감지음이 있으면 폰을 안 봐도 인식 여부를 안다 |
| **피드백의 주 무대는 리플레이** | 폰 앞에 왔을 때 비로소 자세히 본다 |
| **조작은 촬영 전후에 몰아넣는다** | 촬영 중 설정 변경은 불가능하다고 봐야 한다 |

> [D-07](../05-결정/stack/D-07-overlay-rendering.md)에서 Metal 직접 렌더로 지연을 없앴지만, 그 정밀함을 **촬영 중에 볼 사람이 없습니다.** 실시간 오버레이의 진짜 용도는 "제대로 잡히고 있다"는 확인이고, 정밀한 판정은 리플레이에서 합니다. [스켈레톤 오버레이 4.2](../02-설계/SKELETON-OVERLAY.md)의 설계 원칙과 일치합니다.

## 10.2 화면 목록

[WORK-PLAN 9.6](../04-계획/WORK-PLAN.md)의 `Presentation` 모듈에 대응합니다. 아래 6개에 **설정**(10.7)이 더해져 `Settings`까지 7개입니다 — 설정은 탭이 아니므로 이 표에 넣지 않습니다.

| # | 화면 | 모듈 | 역할 | 사용 시점 |
|---|---|---|---|---|
| 1 | **온보딩** | `Onboarding` | 카메라 배치 안내, 권한, 프로필 | 최초 1회 |
| 2 | **촬영** | `Capture` | **모드 선택** → 프레이밍 → 촬영 → 실시간 오버레이 | 코트에서 |
| 3 | **세션 요약** | `Session` | 방금 친 세션의 스윙 목록·분포·점수 | 촬영 직후 |
| 4 | **스윙 리플레이** | `Analysis` | 슬로우 모션 + 스켈레톤 + 페이즈 + **피드백** | ★ 핵심 |
| 5 | **보관함** | `Library` | 과거 세션·클립 탐색 | 집에서 |
| 6 | **진척도** | `Progress` | 기간별 지표 추이 | 주 단위 |

**4번이 이 앱의 심장입니다.** 나머지는 4번으로 가는 경로이거나 4번의 집계입니다.

### 탭바 — 3개 고정

```
┌────────┬────────┬────────┐
│  촬영   │  보관함 │ 진척도  │
└────────┴────────┴────────┘
```

탭 하나가 **할 일 하나**입니다 — 찍는다 / 찾는다 / 본다.

| 탭 | 루트 화면 | 하위 |
|---|---|---|
| **촬영** | 상황 선택 + 시작 | 프레이밍 가이드 → 촬영 중 → 세션 요약 |
| **보관함** | 세션 목록 (유형 필터) | 세션 요약 → 스윙 리플레이 |
| **진척도** | 기간별 추이 | 특정 스윙 → 스윙 리플레이 |

**설정은 탭이 아닙니다.** 할 일이 아니라 준비이므로 `촬영` 탭 우상단 기어 아이콘으로 들어갑니다. 탭을 4개로 늘리면 코트에서 오탭이 늘고, 설정은 세션당 0~1회 쓰는 화면입니다.

**온보딩·촬영 중·세션 요약에는 탭바가 없습니다.** 전자는 최초 1회이고, 나머지 둘은 흐름 중간이라 탭 이동이 세션을 끊습니다.

## 10.3 주 흐름

```
[온보딩] ─최초 1회─┐
                   ▼
              ┌─────────┐
              │  홈/촬영 │◄──────────────┐
              └────┬────┘               │
                   │ 촬영 시작           │
                   ▼                    │
         ┌──────────────────┐           │
         │   촬영 중         │           │
         │  (6m 밖 가독성)   │           │
         │  스윙 감지음 ♪    │           │
         └────────┬─────────┘           │
                  │ 종료                 │
                  ▼                     │
           ┌─────────────┐              │
           │  세션 요약   │──이어서 촬영──┘
           └──────┬──────┘
                  │ 스윙 선택
                  ▼
           ┌─────────────┐
           │ 스윙 리플레이 │  ★ 피드백이 여기 있다
           └─────────────┘

[보관함] ──→ 세션 요약 ──→ 스윙 리플레이   (같은 목적지)
[진척도] ──→ 특정 스윙 ──→ 스윙 리플레이
```

**모든 경로가 리플레이로 수렴합니다.** 보관함과 진척도는 별도 목적지가 아니라 리플레이로 가는 다른 입구입니다.

### 라인 판정은 수렴하지 않는다

관찰 대상이 라인 판정이면 산출물이 **스윙이 아니라 바운스 위치**입니다. 스윙 폼과 무관하므로 리플레이로 가지 않습니다.

```
[촬영 · 라인 판정] ──→ [세션 요약]
                          └─ 판정 탭 — 코트 평면도 + 바운스 점
```

세션 요약이 **탭 둘**을 갖습니다 — `스윙`과 `판정`. 판정 탭은 라인 판정 세션에만 나타납니다.

### 촬영 전 단계

```
[촬영 탭 루트]  상황 선택 (+ 시합이면 관찰 대상)
      │
      ├─ 라인 판정이면 ─→ [코트 프리셋]  4점 탭 → 격자 검증
      │                        │
      ▼                        ▼
[프레이밍 가이드]  상황·관찰 대상에 따라 안내가 다르다
      │
      ▼
[촬영 중]
```

**코트 프리셋은 재사용합니다.** 같은 코트·같은 삼각대 위치면 호모그래피가 같으므로, 저장해 두고 다음에는 격자만 3초 확인합니다. 세션마다 4점을 다시 찍으면 라인 판정을 쓰지 않게 됩니다.

## 10.4 촬영 상황 — 앱이 무엇을 알아야 하는가

✅ **확정** — **상황 하나만 묻고 나머지는 도출한다.**

### 용어

`ADR-0004`가 "촬영 모드"로 부르던 것과 이 절이 부르던 것이 **서로 다른 축**이었습니다. 이름을 갈랐습니다.

| 용어 | 값 | 무엇을 바꾸나 |
|---|---|---|
| **촬영 상황** | 볼머신 · 벽치기 · 랠리 · 시합 · 레슨 | 아래 전부 |
| **관찰 대상** | 내 스윙 / 라인 판정 | **삼각대 배치** ([ADR-0004](../05-결정/adr/ADR-0004-line-call-mode.md)) |

"모드"라는 말은 쓰지 않습니다.

### 왜 상황을 묻는가 — 피드백의 타당성

[ADR-0003](../05-결정/adr/ADR-0003-rule-based-evaluation.md)의 룰 엔진은 `followThroughAngle` 같은 임계로 판정합니다. **벽치기는 팔로스루가 구조적으로 잘립니다** — 벽이 가까워 공이 바로 돌아옵니다.

앱이 맥락을 모르면 **매 스윙마다 "팔로스루가 부족합니다"** 를 냅니다. 사실이지만 쓸모없고, 사용자는 앱이 맥락을 모른다고 판단합니다. 10.8이 신뢰도로 톤을 나누는데, **맥락 자체를 안 받으면 그 장치가 작동하지 않습니다.**

### 상황별로 달라지는 것

| 상황 | 스윙 검출 | 궤적 | 무효화할 룰 | 왕복 빈도 |
|---|---|---|---|---|
| **볼머신** | 일정 간격이 강한 사전정보 | 나가는 쪽만 | — | 없음 |
| **벽치기** | 스윙이 압축돼 임계를 낮춘다 | **돌아오는 공도 잡힌다** ⚠️ | 팔로스루 | 없음 |
| **랠리 (반코트)** | 보통 | 짧은 궤적 | 스윙 길이·구속 | 중간 |
| **랠리 (풀코트)** | 보통 | 정상 | — | 중간 |
| **시합** | 보통 | 정상 | — | 적음 |
| **레슨** | 보통 | 정상 | — | 잦음 |

> ⚠️ **벽치기의 기술적 문제**: `DetectTrajectoriesRequest`가 돌아오는 공도 궤적으로 잡습니다. 임팩트 ±3프레임 매칭이 엉뚱한 궤적에 붙어 검출률이 왜곡될 수 있습니다. [Phase 0 게이트](../02-설계/CAPTURE-PROTOCOL.md)를 벽에서 재면 안 되는 이유이기도 합니다 — 프로토콜 5.5의 기준 조건에 벽치기는 없습니다.

### 왕복 빈도는 묻지 않는다

**상황에서 나옵니다.** 볼머신이면 왕복이 없고, 코치가 있으면 잦습니다. 질문을 하나로 줄이는 것보다 중요한 것은 **사용자가 답하기 쉽다는 점**입니다 — "연속 모드"는 앱의 개념이지만 "볼머신"은 눈앞의 사실입니다.

| 왕복 빈도 | 따라오는 것 |
|---|---|
| 없음 (볼머신·벽치기) | 감지음 필수, 중간 확인 화면 없음, 피드백은 세션 후 |
| 중간 (랠리·시합) | 중간 확인 화면 제공 |
| 잦음 (레슨) | 감지음 기본 꺼짐(코치 방해), 즉석 리플레이 위주 |

### 라인 판정은 시합에만 붙는다

볼머신·벽치기에는 판정할 라인이 없고, 랠리 연습에서 인/아웃을 다툴 일도 없습니다. **`시합`을 고를 때만 관찰 대상 선택이 나타납니다.**

### 선택은 항상 보인다

> **되돌리는 비용이 물리적인 선택은 숨기지 않는다. 소프트웨어로 되돌릴 수 있는 것만 접어둔다.**

| | 잘못 고르면 | 처리 |
|---|---|---|
| **촬영 상황** | 룰이 어긋나 피드백이 무의미 | **항상 노출** |
| **관찰 대상** | **삼각대 재배치 1~2분** | **항상 노출** (시합에서만) |
| 정밀도 120/60 | 품질 차이, 재촬영 불필요 | 접어둠 |
| 코트 프리셋 | 격자 검증이 즉시 잡아냄 | 접어둠 |

지난 선택을 미리 골라두므로 **탭 수는 늘지 않습니다.** 달라지는 것은 어디로 들어가는지가 **항상 보인다**는 점입니다.

**실제 순서가 이렇기 때문입니다.**

```
코트 도착 → 삼각대 세움 → 폰 거치 → 앱 켬
```

앱을 켠 시점에 폰은 이미 놓여 있습니다. 선택 후에 "저기 놓으셔야 했어요"라고 하면 늦으므로, **각 선택지에 배치를 함께 적습니다.**

### 세션 비교

상황이 다르면 나란히 놓지 않습니다. **볼머신과 벽치기를 한 묶음으로 다루면 안 됩니다** — 스트로크 길이 자체가 다릅니다. 상황을 세션 메타에 기록해 `진척도`가 같은 조건끼리 비교하게 합니다.

## 10.5 촬영 중 화면 — 6m 가독성

### 2층으로 나눈다

화면 하나가 **두 거리에서 읽힙니다.** 촬영 중에는 6m 밖이고, 끝내러 왔을 때는 30cm입니다.

| 층 | 요소 | 표현 | 6m |
|---|---|---|---|
| **1층 (6m용)** | 인식 상태 | 스켈레톤 오버레이 자체 | ✅ 사람 형태가 보이면 OK |
| | 스윙 카운트 (라인 판정은 **판정 결과**) | **초대형 숫자 72px** | ✅ |
| | 이상 상태 | 화면 테두리 색 (정상=없음 / 경고=주황 / 오류=빨강) | ✅ |
| **2층 (폰 앞용)** | 경과 시간 · 상황 · 정밀도 | 작게, 가장자리 | ❌ 안 읽힘 |

**2층은 6m에서 안 읽히지만 방해도 하지 않습니다.** 폰 앞에 왔을 때 "이게 무슨 세션이었지"의 답이 되므로 둡니다 — `CaptureWarning` 목업의 `12:04 · 랠리 · 120fps`가 이것입니다.

**수치·설정·피드백은 어느 층에도 넣지 않습니다.** 읽을 수 없고, 읽으려 다가오면 촬영이 끊깁니다.

### 소리 설계

화면보다 중요합니다.

| 이벤트 | 소리 |
|---|---|
| 스윙 감지 | 짧은 톤 1회 — "잡혔다" |
| 인식 실패(프레임 이탈 등) | 낮은 톤 — "다시" |
| 흔들림·발열 경고 | 경고음 + 테두리 색 |
| 녹화 시작/종료 | 구분되는 톤 |

**스윙 감지음만 있어도 폰을 안 봐도 됩니다.** 이게 왕복 횟수를 줄이는 가장 큰 장치입니다.

### 라인 판정의 소리

관찰 대상이 라인 판정이면 소리가 더 중요합니다 — **플레이어는 공을 보고 있지 폰을 보지 않습니다.**

| 판정 | 소리 | 색 |
|---|---|---|
| 명백한 인 | 짧고 낮은 톤 | `state/success` |
| 명백한 아웃 | 짧고 높은 톤 — 인과 **분명히 구분** | `state/error` |
| 판정 불가 | 중립적인 톤 | `text/tertiary` |

시각 표현은 [DESIGN-SYSTEM 11.6](DESIGN-SYSTEM.md)이 정본입니다 — 72px 텍스트가 주, 색은 보조, 판정 불가에는 테두리·펄스를 쓰지 않습니다.

**"판정 불가"는 실패음이 아니어야 합니다.** 정직한 결과이지 오류가 아닙니다. 오류음으로 내면 사용자는 앱이 고장났다고 읽습니다.

> 세 소리가 코트에서 실제로 구분되는지는 **실기기에서 들어봐야** 정해집니다 (10.10).

## 10.6 예외 경로

성공 경로만 설계하면 코트에서 막힙니다. 실제로 벌어지는 것들입니다.

| 상황 | 감지 | 화면 | 사용자가 할 수 있는 것 |
|---|---|---|---|
| **카메라 권한 거부** | 온보딩 | 차단 화면 | 설정 앱으로 이동 |
| **마이크 권한 거부** | 온보딩 | 경고만 | **무음 녹화로 계속** — 핵심 기능이 아니다 |
| **저장공간 부족** | 촬영 시작 전 | 예상 용량과 남은 용량 비교 | 정밀도를 60fps로 낮추기 / 보관함 정리 |
| **발열 (`thermalState`)** | 촬영 중 | 단계별 (아래) | 정밀도 낮추기 / 잠시 쉬기 |
| **흔들림** | 촬영 중 | 테두리 주황 + 경고음 | 삼각대 확인 |
| **앱 강제 종료** | 다음 실행 | "지난 세션이 끝나지 않았습니다" | 복구 / 폐기 |
| **스윙 0개로 종료** | 세션 종료 | **진단 화면** (요약 아님) | 배치 재확인 안내 |
| **잘못 찍힌 클립** | — | 보관함 스와이프 / 리플레이 메뉴 | 삭제 |

### 발열은 단계로 대응한다

[성공 기준](../01-제품/PRODUCT-OVERVIEW.md)이 "연속 15분 촬영 시 스로틀링 없음"을 요구합니다. 그래도 넘으면 **조용히 느려지는 것이 가장 나쁩니다** — 사용자는 계속 치고 있는데 기록이 빠집니다.

| `thermalState` | 대응 |
|---|---|
| `.nominal` `.fair` | 아무것도 하지 않음 |
| `.serious` | 테두리 주황 + **"120fps를 60fps로 낮출까요"** 제안 |
| `.critical` | 테두리 빨강 + 경고음 + **녹화 중단**, 지금까지 기록은 저장 |

### 스윙 0개는 요약이 아니라 진단이다

빈 세션 요약을 보여주면 사용자는 **앱이 고장났다고 판단합니다.** 원인을 짚어야 합니다.

```
스윙을 하나도 찾지 못했습니다

확인할 것
  · 선수가 프레임 안에 들어왔나요
  · 삼각대가 흔들리지 않았나요
  · 거리가 5~8m 범위였나요

[ 배치 다시 보기 ]   [ 영상 확인 ]
```

**영상은 지웁니다** — 스윙이 없으면 저장할 가치가 없습니다. 다만 사용자가 직접 확인할 수 있게 한 번은 보여줍니다.

## 10.7 설정

`촬영` 탭 우상단 기어로 들어갑니다. **탭이 아닙니다** — 할 일이 아니라 준비이고, 세션당 0~1회 씁니다.

| 묶음 | 항목 |
|---|---|
| **프로필** | **주 사용 손 (좌/우)** · 이름 |
| 소리 | 감지음 on/off · 볼륨 · 판정음 on/off |
| 촬영 | 기본 정밀도 (120/60) · 기본 촬영 상황 |
| 라인 판정 | **코트 프리셋 관리** (추가·이름 변경·삭제) |
| 데이터 | 저장공간 사용량 · 전체 삭제 |
| 정보 | 버전 · 오픈소스 라이선스 |

### 주 사용 손은 설정이 아니라 전제다

**분석의 전제**이므로 온보딩에서 **반드시** 받습니다. 나중에 바꿀 수 있게 설정에도 두지만, 비워둔 채로 촬영에 들어갈 수 없습니다.

무엇에 쓰는가:

| 쓰이는 곳 | 없으면 |
|---|---|
| 스켈레톤의 **라켓 팔**(시안색) 지정 | 어느 팔을 강조할지 모른다 |
| 포핸드/백핸드 분류 | 좌우가 뒤집힌다 |
| 배치 안내 | 선수의 앞/뒤 중 어느 쪽이 카메라를 향하는지 달라진다 |

세 번째는 **프로토콜 5.1이 아직 다루지 않는 부분**입니다. 측면 6m는 정했지만 **어느 쪽 측면인지**는 정하지 않았습니다. 오른손잡이를 오른쪽에서 찍는 것과 왼쪽에서 찍는 것은 보이는 몸이 다릅니다.



## 10.8 스윙 리플레이 — 피드백을 어떻게 보여줄 것인가

[ADR-0003](../05-결정/adr/ADR-0003-rule-based-evaluation.md)이 원칙을 정했습니다. 그걸 화면으로 옮깁니다.

| ADR 원칙 | 화면 구현 |
|---|---|
| 한 번에 하나를 고치게 한다 | **피드백 1개를 크게**, 나머지는 접어둔다 |
| 원인이 아니라 동작을 지시한다 | "앞발에 체중을 더 실어보세요" (❌ "체중 이동 부족") |
| 수치를 함께 보여준다 | 지시 아래 작게 `112° · 권장 150~170°` |
| 틀릴 수 있음을 인정한다 | **신뢰도로 표현을 나눈다 (아래)** |

### ✅ 톤 — 신뢰도로 구분한다

확정 사항이다. 하나의 톤으로 통일하지 않는다.

| 신뢰도 | 표현 | 예 |
|---|---|---|
| **높음** — 룰 임계를 확실히 벗어남 | **지시형** | "앞발에 체중을 더 실어보세요" |
| **낮음** — 임계 근처 · 관절 confidence 낮음 · 표본 부족 | **제시형** | "임팩트 시 팔꿈치 112°입니다. 권장 범위는 150~170°입니다" |

지시형은 초보자에게 친절하지만 틀리면 신뢰를 크게 잃습니다. 제시형은 안전하지만 초보자가 무엇을 고칠지 모릅니다. **확실할 때만 단언**하는 것이 [ADR-0003](../05-결정/adr/ADR-0003-rule-based-evaluation.md)의 "틀릴 수 있음을 인정한다"와 맞습니다.

시각적으로도 구분합니다 — 지시형은 강조 색과 큰 타이포, 제시형은 중립 색과 본문 타이포.

### 화면 구성

```
┌────────────────────────────────┐
│  영상 + 스켈레톤 (슬로우 모션)    │
│                                │
│  ◄──────●────────────────────► │  페이즈 스크러버
│  준비 테이크백 포워드 임팩트 팔로 │
├────────────────────────────────┤
│  앞발에 체중을 더 실어보세요       │  ← 지시 (크게)
│  112° · 권장 150~170°           │  ← 근거 (작게)
│                                │
│  ▸ 다른 지적 2개                 │  ← 접힘
└────────────────────────────────┘
```

**페이즈 스크러버가 핵심 인터랙션**입니다. 임팩트 프레임으로 한 번에 이동할 수 있어야 하고, 기본 재생 위치도 임팩트여야 합니다 — 대부분의 지표가 그 프레임에서 계산되기 때문입니다.

- ⬜ **"판정 불가"를 코트에서 어떻게 말할 것인가** — 세 소리가 실제로 구분되는지 들어봐야 한다 (10.5절)
