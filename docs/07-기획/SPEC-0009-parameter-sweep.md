# SPEC-0009. 파라미터 스윕 및 검출률 집계

> 이슈 [#9](https://github.com/wnsgur9137/TeniTeni/issues/9) · 마일스톤 `0-C 검증`

## 배경

0-C의 마지막 도구이자 **Phase 0 게이트 판정을 내리는 도구**입니다. 조건을 바꿔가며 검출률을 집계하고 [프로토콜 5.5](../02-설계/CAPTURE-PROTOCOL.md)의 기준(70 % / 50~70 % / 50 % 미만)으로 결론을 냅니다.

앞선 세 도구가 준비됐습니다 — [`teni synth`](SPEC-0006-synthetic-video.md), [`teni analyze`](SPEC-0007-analyze-cli.md), [`teni label`](SPEC-0008-label-tool.md).

착수 전 조사([검출 평가 지표](../08-레퍼런스/ml/DetectionMetrics.md))에서 하나가 드러났습니다.

**게이트가 recall만으로 판정합니다.** 우리 "검출률"은 표준의 recall이고, 오검출은 기록되지만 판정에 들어가지 않습니다. `objectMaximumNormalizedRadius`를 키우고 `trajectoryLength`를 최소로 두면 recall이 오르는 대신 헛검출이 늘어나는데, **판정 기준이 recall이면 스윕이 그 방향으로 몰아갑니다.**

## ⚠️ 이 작업이 게이트를 판정하지 못합니다

**실영상이 없습니다.** 프로토콜 5.5는 분모를 "영상을 사람이 보며 센 실제 타구"로 정하고, 게이트는 **실외 맑음·단순 배경·120 fps · 최소 30타구**에서 판정합니다. 0-B 촬영이 선행 조건입니다.

이 작업의 산출물은 **판정 도구와 그 검증**입니다. 실영상이 오면 명령 한 줄로 판정이 나오는 상태를 만듭니다.

합성 영상으로 도는 스윕은 **도구가 동작함을 보이는 것**이고, 거기서 나온 숫자는 게이트 값이 아닙니다.

## 범위

### 만들 것

- `teni sweep` 서브커맨드
- 조건 조합 생성 — `trajectoryLength` · radius 범위 · 노출 · 거리
- 조건마다 `synth` → `analyze`를 돌려 결과 수집 (합성 모드)
- **기존 클립 디렉터리를 받아 파라미터만 스윕** (실영상 모드)
- **precision · recall · F1** 산출
- 프로토콜 5.5 기준으로 판정 출력
- 조건별 표 + 요약 JSON

### 만들지 않을 것

- **게이트 판정 기준 변경** — recall 기준 그대로 판정합니다. precision이 낮으면 **경고만** 합니다. 기준을 바꾸는 것은 사람의 판단입니다
- **실영상 촬영·라벨링** — 0-B와 #8
- **최적 파라미터 자동 채택** — 표를 내고 사람이 고릅니다. recall만 보고 자동으로 고르면 위에서 말한 함정에 빠집니다
- **accuracy · FPR** — TN이 정의되지 않습니다 ([조사](../08-레퍼런스/ml/DetectionMetrics.md) 3절)
- **병렬 실행** — 아래 참고

## 구현 선택지

### 1. 조합 폭발을 어떻게 다루는가

축이 넷입니다. 전수 조합은 금방 수백 개가 됩니다.

| 선택지 | 장점 | 단점 |
|---|---|---|
| **A. 축별 1차원 스윕 (OFAT)** | 조합 수가 축 길이의 합. 어느 축이 중요한지 바로 보인다 | 축 간 상호작용을 놓친다 |
| B. 전수 조합 | 상호작용까지 본다 | 4축 각 4값이면 256조합. 합성·분석 시간이 감당 안 된다 |
| C. 무작위 탐색 | 넓게 훑는다 | 재현·해석이 어렵다 |

**채택: A.** 기본값에서 한 축씩 움직입니다. 상호작용이 의심되면 `--grid`로 두 축만 교차할 수 있게 둡니다.

### 2. 합성 영상을 매번 만들 것인가

노출·거리를 바꾸면 영상이 달라집니다. 1/60 s 조건은 하위 표본이 106장이라 생성이 느립니다.

**채택: 조건별 캐시.** 같은 합성 조건이면 만들어 둔 `.mov`를 재사용합니다. 파일명에 조건을 인코딩해 판정합니다.

`trajectoryLength`·radius는 **분석 파라미터**라 영상이 같습니다 — 이 축들은 한 영상으로 전부 돕니다.

### 3. 병렬 실행

**채택: 하지 않습니다.** Vision 요청이 ANE를 쓰고, 동시에 여러 개를 돌리면 서로 느려집니다. 무엇보다 **0-C는 한 번 돌리고 판정하는 작업**이라 최적화할 대상이 아닙니다. 느리면 축을 줄입니다.

## 완료 기준

- [x] `teni sweep --help`가 파라미터 목록을 출력
- [x] 합성 모드로 축별 스윕이 돌고 조건별 표가 나옴
- [x] **precision · recall · F1이 전부 산출됨**
- [x] 프로토콜 5.5 기준(70 / 50~70 / 50)으로 판정이 출력됨
- [x] precision이 낮은 조건에 경고가 붙음
- [x] `--clips <디렉터리>`로 **기존 클립을 받아** 파라미터만 스윕할 수 있음
- [x] 요약 JSON이 저장됨
- [x] `scripts/verify-ios.sh` 통과, 경고 0

## 검증 방법

| 항목 | 방법 |
|---|---|
| 게이트 | `scripts/verify-ios.sh` |
| 지표 계산 | precision·recall·F1을 인위적 입력으로 단위 테스트 고정 |
| 판정 경계 | 69.9 / 70 / 50 / 49.9 %의 판정이 프로토콜과 맞는지 |
| 실제 스윕 | 합성 영상으로 노출 축을 돌려 **1/1000s가 1/250s보다 나은지** |

마지막이 의미 있습니다. **노출 가설이 실험으로 확인되는 첫 지점**입니다 — 지금까지는 계산과 문헌으로만 뒷받침됐습니다.

## 구현 중 찾은 결함 — 검출 0의 원인을 알 수 없었다

해상도를 줄여 회전을 빠르게 하려고 `--height 360`으로 돌렸더니 **8 m 조건만 빼고 전 조건이 0 %** 였습니다.

```
[1/9] 기준 recall 0.0% precision 0.0%
[2/9] 노출 recall 0.0% precision 0.0%
...
[5/9] 거리 recall 100.0% precision 100.0%   ← 8m만
```

원인은 검출기가 아니라 **영상**이었습니다. 세로를 줄이자 공이 프레임 위로 벗어났고, 8 m에서는 px/m이 작아 화면 안에 남았습니다.

**도구가 그것을 알려주지 못했습니다.** 스윕 결과를 보고 "검출기가 나쁘다"고 결론 내릴 수 있었습니다.

정답 좌표가 화면 밖으로 나간 비율을 검사해 30 %를 넘으면 경고합니다.

```
⚠️ 공이 프레임을 벗어난 비율 86% — 검출 0은 영상 문제일 수 있습니다. 해상도를 키우세요
```

**검출 0이 검출기 문제인지 영상 문제인지 구분하는 장치**입니다. 이것이 없으면 스윕 결과를 해석할 수 없습니다.

## 리스크

| 리스크 | 영향 | 대응 |
|---|---|---|
| **합성 스윕 결과를 게이트 값으로 오해** | Phase 1을 잘못된 근거로 진행 | 출력에 "합성 영상 — 게이트 값 아님"을 명시. 실영상 모드와 출력을 구분 |
| recall 기준이 헛검출 많은 설정을 뽑음 | 실사용 불가한 파라미터 채택 | precision을 함께 내고 경고. 자동 채택하지 않음 |
| 합성 영상이 쉬워 전 조건 100 % | 축 간 차이가 안 보임 | 노이즈·배경을 어렵게 만들어 변별력을 낸다. 그래도 평평하면 그 사실을 보고한다 |
| 스윕이 너무 오래 걸림 | 반복 불가 | OFAT + 영상 캐시. 해상도·길이를 줄인 예비 스윕 지원 |

## 미수행으로 남길 것

- **실제 게이트 판정** — 0-B 촬영과 #8 라벨링이 선행입니다. **이 작업으로 Phase 0 게이트가 판정되지 않습니다**
- **실영상 오검출 양상** — 합성에서는 배경이 균일해 헛검출이 거의 없습니다
- **precision 하한 결정** — 어느 정도가 "쓸 만한가"는 실영상을 봐야 정할 수 있습니다
