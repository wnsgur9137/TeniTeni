# SPEC-0121. 리플레이 오버레이 레이어

> 이슈 [#121](https://github.com/wnsgur9137/TeniTeni/issues/121) · 결정 [ADR-0006](../05-결정/adr/ADR-0006-replay-overlay-layers.md)

## 배경

오버레이를 **촬영 중에 보여주지 않습니다.** 리플레이에서 사용자가 골라 켭니다. 그 결정과 근거는 [ADR-0006](../05-결정/adr/ADR-0006-replay-overlay-layers.md)에 있으므로 재론하지 않습니다.

네 레이어 중 **둘만 지금 만들 수 있습니다.**

| 레이어 | 입력 | 선행 | 이 작업 |
|---|---|---|---|
| **스켈레톤** | `DetectHumanBodyPoseRequest` | 없음 | ✅ |
| **라켓 궤적** | `detectsHands` 손 관절 + 어깨너비 스케일 | 없음 | ✅ |
| 볼 궤적 | `DetectTrajectoriesRequest` | **0-C 게이트** ([프로토콜 5.5](../02-설계/CAPTURE-PROTOCOL.md)) | ❌ |
| 라인 | 호모그래피 | **1-F 2·3** ([WORK-PLAN 9.4](../04-계획/WORK-PLAN.md)) | ❌ |

**레이어 구조·사이드카 형식·모드 전환을 지금 세우는 것**이 이 작업의 절반입니다. 나머지 둘은 선행이 풀릴 때 사이드카에 필드를 더하고 모드를 더하면 됩니다.

## 범위

### 만들 것

- `OverlayLayer` — 배타적 모드. `off` / `skeleton` / `racket`
- 클립 저장 직후 사이드카를 굽는 백그라운드 경로
- 사이드카 포맷 — 프레임별 관절·신뢰도, 확장 가능한 구조
- 리플레이에서 사이드카를 읽어 Canvas로 그리는 렌더
- **사이드카가 아직 없을 때의 화면** — 굽는 중 / 실패 / 이 클립은 분석 전
- `PoseJoint`를 트리거용 6개에서 **스켈레톤용 전체**로 확장
- 마지막으로 고른 모드를 기억

### 만들지 않을 것

| 항목 | 왜 |
|---|---|
| 볼 궤적 · 라인 레이어 | 선행이 안 풀렸다. 모드 열거형에 자리만 비워 둔다 |
| 오버레이를 **구운** 영상 내보내기 | Canvas로는 안 된다. ADR-0006이 "필요해지면 그때 Metal 렌더러를 따로 만든다"로 정했다 |
| 라켓 **면 각도** | [PRODUCT-OVERVIEW](../01-제품/PRODUCT-OVERVIEW.md)가 "센서 없이 영상만으로는 신뢰도 확보 불가"로 범위 밖에 뒀다 |
| 레퍼런스 고스트 | [스켈레톤 오버레이 4.7](../02-설계/SKELETON-OVERLAY.md)이 신체 비율 정규화·DTW 선행으로 Phase 2에 뒀다 |
| 문제 관절 강조 · 각도 라벨 | 룰 엔진(1-D)이 만든다. 지금은 강조할 이탈 관절이 없다 |
| One Euro Filter | 떨림 제거는 **별 작업으로 둔다.** 사이드카가 생기면 굽는 단계에 끼우면 되고, 끼우기 전에도 그릴 수 있다 |
| 라이브 오버레이 | ADR-0006 선택지 3에서 거부 |

## 라켓 궤적 — 추정식과 그 한계

**라켓을 찾아주는 API가 없습니다.** 손 관절에서 추정합니다. 이 절이 이 작업에서 가장 약한 고리이므로 식과 한계를 명시합니다.

### 입력

`HumanBodyPoseObservation.rightHand` / `.leftHand`가 `HumanHandPoseObservation`을 줍니다(손목 + 손가락 21관절). 주 사용 손은 온보딩에서 받은 `handedness`로 고릅니다.

### 식

```
u          = normalize(middleMCP − wrist)          ← 그립 축 (손바닥 긴 방향)
mPerNorm   = SHOULDER_M / shoulderWidth_norm       ← 어깨너비를 자로 쓴다
head       = wrist + u × (GRIP_TO_HEAD_M / mPerNorm)
```

| 상수 | 값 | 근거 |
|---|---|---|
| `SHOULDER_M` | 0.40 m | 성인 평균 양어깨 너비. **개인차를 무시한다** |
| `GRIP_TO_HEAD_M` | 0.42 m | ITF 최대 전장 0.685 m, 손이 버트에서 약 0.10 m 위, 헤드 중심이 버트에서 약 0.52 m |

`shoulderWidth(minimumConfidence:)`는 **이미 있습니다** — 사람을 고르는 기준으로 쓰고 있으므로 자를 새로 만들지 않습니다.

### 2D 투영의 한계를 숨기지 않는다 — 단축(foreshortening)을 계산한다

라켓이 카메라 쪽이나 반대쪽을 향하면 투영 길이가 줄어 **헤드가 실제보다 멀리 찍힙니다.** 깊이를 모르므로 보정할 수 없습니다.

그런데 **의심할 수는 있습니다.** 손 자체가 같이 단축되기 때문입니다.

```
expectedHand = HAND_M / mPerNorm          HAND_M = 0.10 m (손목→middleMCP)
foreshorten  = clamp(|middleMCP − wrist| / expectedHand, 0, 1)
```

손이 기대보다 짧게 보이면 라켓도 그만큼 단축됐다는 뜻입니다. 이 값을 신뢰도에 곱합니다.

```
confidence = min(wrist.conf, middleMCP.conf) × foreshorten
```

**임계 미달 구간은 선을 끊습니다.** 이어 그리면 틀린 위치를 확신 있게 보여주는 것이 되고, 그것이 추정을 숨기는 것보다 나쁩니다. 신뢰도 → 투명도 매핑은 [4.7의 기존 원칙](../02-설계/SKELETON-OVERLAY.md)을 그대로 씁니다.

### 그래도 남는 한계

- **서브와 극단적 팔로스루에서 틀어집니다.** 측면 6m 배치([프로토콜 5.1](../02-설계/CAPTURE-PROTOCOL.md))는 스윙 평면을 카메라와 평행하게 두지만 서브는 그 평면을 벗어납니다
- **임팩트 순간의 손 관절이 가장 안 믿을 만합니다.** 모션 블러와 라켓 자체의 가림 — 하필 사용자가 제일 주목하는 프레임입니다
- **정답이 없습니다.** 정확도를 수치로 판정할 방법이 없고 "그럴듯한가"까지만 봅니다
- 개인차(어깨너비·라켓 길이)를 무시합니다. 설정으로 받는 것은 범위 밖입니다

화면에 **"추정"이라고 적습니다.** 사용자가 측정값으로 읽으면 안 됩니다.

## 구현 선택지

### 1. 사이드카를 어디에 두는가

| 선택지 | 장점 | 단점 |
|---|---|---|
| **클립 파일 옆 `.overlay.json`** | 클립과 수명이 같다. 지우면 같이 사라진다. 사람이 열어볼 수 있다 | 레코드와 파일이 어긋날 수 있다([#120](https://github.com/wnsgur9137/TeniTeni/issues/120)과 같은 종류) |
| SwiftData에 Blob | 트랜잭션이 하나다 | 프레임 수백 개 × 관절 19개를 DB에 넣는다. 조회가 느려지고 보관함이 그 DB를 읽는다 |
| 메모리에만 | 단순 | 앱을 닫으면 사라진다 — 다시 구워야 한다 |

**채택: 클립 파일 옆 `.overlay.json`.** 보관함([SPEC-0116](SPEC-0116-session-library.md))이 읽는 DB를 무겁게 만들지 않는 것이 결정적입니다. 어긋남은 #120이 다룰 같은 문제이고, 사이드카가 없으면 "분석 전"으로 표시하면 됩니다 — **없는 것이 정상 상태 중 하나입니다.**

JSON을 고른 이유: 포맷이 확장돼야 합니다(볼 궤적·라인이 나중에 들어옵니다). 사람이 열어 확인할 수 있는 것도 0-C 도구들(`teni analyze`)의 출력과 같은 성격입니다.

### 2. 언제 굽는가

| 선택지 | 장점 | 단점 |
|---|---|---|
| **클립 저장 직후 백그라운드** | 리플레이가 즉시 열린다 | 촬영 직후 CPU를 쓴다 — 이어서 찍으면 겹친다 |
| 리플레이를 열 때 | 안 볼 클립은 계산하지 않는다 | **열 때마다 기다린다.** 슬로우 모션 재생 중에 계산이 끼면 끊긴다 |
| 세션 종료 후 일괄 | 겹치지 않는다 | 세션이 길면 수십 클립을 한 번에 — 그동안 아무것도 못 본다 |

**채택: 클립 저장 직후 백그라운드.** 단, **촬영 중에는 돌리지 않습니다** — 라이브 포즈 추정과 CPU를 다투면 스윙 트리거가 신호를 잃습니다. 세션이 끝난 뒤 큐를 비우고, 그 사이 리플레이는 "분석 중"을 보여줍니다.

### 3. 모드 전환 UI

배타적 모드는 [ADR-0006](../05-결정/adr/ADR-0006-replay-overlay-layers.md)이 정했습니다. 남은 것은 표현입니다.

| 선택지 | 장점 | 단점 |
|---|---|---|
| **세그먼트 컨트롤** | 선택지가 한눈에. 지금 뭐가 켜졌는지 명확 | 자리를 차지한다. 레이어가 4개로 늘면 좁다 |
| 아이콘 하나로 순환 | 자리를 아낀다 | **다음에 뭐가 나올지 모른다.** 네 번 눌러야 원하는 것이 온다 |
| 메뉴 | 확장에 강하다 | 두 번 탭 |

**채택: 세그먼트 컨트롤.** 레이어가 4개가 되면 아이콘만 남기고 레이블을 뺍니다. 리플레이는 폰 앞에서 보는 화면이므로 아이콘 네 개가 좁지 않습니다.

### 4. 기본값과 기억

**기본은 `off`입니다.** 리플레이의 첫 화면은 자기 스윙 영상이어야 합니다 — 오버레이는 사용자가 "보고 싶다"고 말한 뒤에 올라옵니다.

마지막으로 고른 모드를 `UserPreferences`에 기억합니다. `lastSituation`·`lastObservable`과 같은 패턴입니다 — 매번 다시 고르게 하지 않습니다.

### 5. `PoseJoint`를 확장하면 가짜 구현이 커진다

`BodyPoseObservable`은 지금 관절 6개만 노출합니다. [SPEC-0096 선택지 2](SPEC-0096-pose-intake.md)가 그렇게 좁힌 이유는 **`HumanBodyPoseObservation`을 합성할 수 없어서** 가짜 구현으로 테스트하기 때문입니다.

스켈레톤은 전체 관절이 필요하므로 노출면이 커집니다. 가짜 구현이 `switch` 몇 줄에서 딕셔너리로 바뀝니다 — **커지지만 여전히 실기기가 필요 없습니다.** 그 성질이 깨지지 않으므로 확장합니다.

## 데이터 모델

```
OverlayLayer        off | skeleton | racket        (+ ball | line 자리)

OverlaySidecar
  version           Int                            포맷이 바뀔 것을 전제한다
  clipFileName      String                         클립과 짝이 맞는지 확인용
  frameRate         Double                         클립의 실제 fps (강등되면 다르다 — ADR-0005)
  frames            [OverlayFrame]

OverlayFrame
  seconds           Double                         클립 시작 기준
  joints            [PoseJoint: Point + confidence]
  racketHead        Point + confidence             nil이면 그 프레임은 끊는다
```

`frameRate`를 사이드카에 적는 이유: 발열로 강등되면 클립마다 fps가 다릅니다([ADR-0005](../05-결정/adr/ADR-0005-thermal-auto-adjust.md)). 리플레이가 세션의 fps를 가정하면 오버레이가 영상과 어긋납니다.

### 좌표계

사이드카는 **Vision의 정규화 좌표(좌하단 원점)를 그대로** 담습니다. 뒤집지 않습니다 — [동시성 6.7](../02-설계/CONCURRENCY.md)의 규약이고 `PoseFrame`이 이미 그 전제입니다.

화면 변환은 `RenderTransform`([SPEC-0040](SPEC-0040-render-transform.md))이 합니다. 각의 출처만 다릅니다 — 라이브는 `RotationCoordinator`, 리플레이는 **비디오 트랙의 `preferredTransform`**입니다.

## 리스크

| 리스크 | 영향 | 대응 |
|---|---|---|
| **라켓 헤드가 눈에 띄게 틀린다** | 신뢰를 잃는다. "추정"이라 적어도 틀린 그림은 틀린 그림이다 | 단축 신뢰도로 끊는다. 실기기에서 보고 **그래도 나쁘면 그립 궤적으로 후퇴**한다 — 그 판단은 보고 나서 한다 |
| 굽는 경로가 촬영과 CPU를 다툰다 | 스윙 트리거가 신호를 잃는다 | 촬영 중에는 큐를 돌리지 않는다. 세션 종료 후에 비운다 |
| 사이드카와 클립이 어긋난다 | 엉뚱한 오버레이 | `clipFileName`과 `frameRate`를 사이드카에 적어 대조한다. 어긋나면 "분석 전"으로 떨어진다 |
| `PoseJoint` 확장이 트리거를 깬다 | 1-B 회귀 | 기존 6개의 매핑을 건드리지 않고 **더하기만** 한다. 기존 테스트가 그대로 돌아야 한다 |
| 긴 클립의 사이드카가 크다 | 디스크·파싱 시간 | 120fps × 10초 × 관절 19개 ≈ 23k 점. **측정 전에 상한을 정하지 않는다** — 실측 후 판단 |
| 레이어가 4개로 늘 때 세그먼트가 좁다 | UI 재작업 | 레이블을 빼고 아이콘만 남기는 경로를 미리 정해 둔다 |

## 미수행으로 남길 것

- ⚠️ **라켓 헤드 추정의 정확도** — 정답이 없다. 실기기에서 사람이 "그럴듯한가"를 본다
- ⚠️ **실기기에서 오버레이가 영상과 맞는지** — 시뮬레이터에서는 Vision이 돌지 않아 사이드카가 비어 있다
- ⚠️ **스크린샷** — 같은 이유
- ⚠️ 사이드카 크기·파싱 시간 실측
- 볼 궤적 레이어 (0-C 게이트 후)
- 라인 레이어 (1-F 호모그래피 후)
- One Euro Filter (별 작업)
- 오버레이를 구운 영상 내보내기
