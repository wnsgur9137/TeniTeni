# SPEC-0008. 임팩트 프레임 라벨링 도구

> 이슈 [#8](https://github.com/wnsgur9137/TeniTeni/issues/8) · 마일스톤 `0-C 검증`

## 배경

게이트 검출률의 **분모**는 사람이 센 타구입니다 ([프로토콜 5.5](../02-설계/CAPTURE-PROTOCOL.md)). 그 분모를 만드는 도구입니다.

착수 전 조사([스포츠 영상 이벤트 라벨링](../08-레퍼런스/ml/EventAnnotation.md))에서 두 가지가 나왔습니다.

- 우리 방식은 **Action Spotting**입니다 — 구간이 아니라 단일 타임스탬프. 문헌 주류와 일치하고 프로토콜이 이미 그렇게 정했습니다
- **우리 ±3프레임 기준이 문헌 표준보다 4배 엄격합니다.** 문헌은 30 fps에서 ±3(100 ms), 우리는 120 fps에서 ±3(25 ms)입니다

두 번째가 이 작업의 설계를 바꿉니다. **사람이 25 ms 안으로 찍지 못하면 검출기가 정확해도 매칭이 실패합니다.**

## 범위

### 만들 것

- `teni label` 서브커맨드
- **컨택트 시트** 생성 — 프레임들을 격자 PNG로 뽑아 눈으로 훑는다
- 확정한 프레임 번호를 `teni analyze --ground-truth`가 읽는 JSON으로 저장
- **자기 일치도 측정** — 같은 클립의 두 라벨링을 비교해 프레임 차이 산출

### 만들지 않을 것

- **대화형 TUI·GUI** — 아래 선택지 참고
- **게이트 기준 변경** — ±3프레임이 현실적인지는 이 도구가 **재기만** 합니다. 기준을 바꾸는 것은 별개 판단이고 사람이 정합니다
- **자동 임팩트 검출** — 수동 라벨링이 목적입니다. 자동화하면 검출기를 검출기로 검증하는 꼴이 됩니다
- **서브/일반 스윙 분류** — 문헌 데이터셋은 나누지만 프로토콜 5.5의 분모는 "라켓에 공이 맞은 횟수"입니다. 분류는 1-B
- **바운드 라벨링** — 같은 이유

## 구현 선택지

### 1. 터미널에서 영상 프레임을 어떻게 보여줄 것인가

핵심 문제입니다. 임팩트를 찾으려면 연속 프레임을 빠르게 훑어야 하는데 터미널에 영상이 안 나옵니다.

| 선택지 | 장점 | 단점 |
|---|---|---|
| **A. 컨택트 시트 PNG** | 한 장에 수십 프레임. 미리보기에서 확대·스크롤이 공짜. 파일로 남아 재현된다 | 프레임 번호를 사람이 읽고 타이핑해야 한다 |
| B. 프레임마다 `qlmanage` 창 | 한 프레임을 크게 본다 | 프레임당 창 하나. 120 fps에서 훑기 불가능 |
| C. iTerm2 인라인 이미지 | 터미널 안에서 완결 | **터미널 의존.** 다른 환경에서 안 보인다 |
| D. SwiftUI macOS 앱 | 제대로 된 스크러버 | 0-C 범위를 크게 넘는다. 앱 타깃이 하나 더 생긴다 |

**채택: A.** 2단계로 씁니다.

```
1. teni label clip.mov --sheet          전체를 성기게 훑어 타구 구간 찾기
2. teni label clip.mov --sheet --around 36 --span 20   그 구간을 프레임별로 확대
3. teni label clip.mov --mark 36,216,396 --out truth.json
```

**시트에 프레임 번호를 새깁니다.** 번호가 없으면 몇 번째인지 세야 하고 그게 틀리면 라벨 전체가 어긋납니다.

### 2. 자기 일치도를 어떻게 재는가

**채택: `--compare a.json b.json`.** 같은 클립을 두 번 라벨링한 결과를 받아 타구별 프레임 차이와 평균 절대 차이를 냅니다.

출력에 **±3프레임 기준 충족 여부**를 함께 적습니다. 넘으면 게이트 기준이 사람의 정밀도보다 엄격하다는 증거가 됩니다.

### 3. 격자 크기

**채택: 열 개수만 인자로 받고 행은 프레임 수에서 자동 결정.** 기본 6열.

썸네일 크기는 기본 320px 폭입니다. 1920px 원본을 6열로 놓으면 한 장이 1920px 폭이 되어 미리보기에서 다루기 좋습니다.

## 완료 기준

- [ ] `teni label --help`가 파라미터 목록을 출력
- [ ] `--sheet`가 프레임 번호가 새겨진 PNG를 생성
- [ ] `--around` + `--span`으로 특정 구간을 프레임 단위로 뽑을 수 있음
- [ ] `--mark`로 만든 JSON을 `teni analyze --ground-truth`가 **그대로 읽음**
- [ ] `--compare`가 두 라벨링의 프레임 차이와 평균 절대 차이를 출력
- [ ] `--compare`가 ±3프레임 기준 충족 여부를 명시
- [ ] `scripts/verify-ios.sh` 통과, 경고 0

## 검증 방법

| 항목 | 방법 |
|---|---|
| 게이트 | `scripts/verify-ios.sh` |
| 포맷 호환 | `teni synth` → `teni label --mark` → `teni analyze --ground-truth` 왕복 |
| 프레임 번호 정확성 | 합성 영상의 정답 프레임과 시트의 번호가 일치하는지 |
| 일치도 계산 | 인위적 두 라벨링을 넣어 평균 절대 차이를 단위 테스트로 고정 |

**시트가 실제로 읽히는지는 사람이 봐야 합니다.** 생성 여부와 번호 정확성까지가 자동 검증 범위입니다.

## 리스크

| 리스크 | 영향 | 대응 |
|---|---|---|
| **사람이 ±3프레임 안으로 못 찍는다** | 검출률이 낮게 나와 게이트를 오판 | `--compare`로 잰다. 넘으면 기준 재검토를 제안하되 **바꾸지는 않는다** |
| 컨택트 시트로 임팩트를 못 가린다 | 라벨링 불가 | 1/1000s 노출에서 공이 15px이고 블러가 6px이다. 320px 썸네일이면 공이 2.5px — **부족할 수 있다.** `--thumb-width`로 키울 수 있게 한다 |
| 프레임 번호 계산이 어긋남 | 라벨 전체가 밀린다 | 합성 영상의 정답과 대조해 테스트로 고정 |
| 시트 생성이 느림 | 라벨링 회전 저하 | 성기게 훑는 1단계는 간격을 두어 프레임 수를 줄인다 |

## 미수행으로 남길 것

- **실제 라벨링 수행** — 실영상이 있어야 합니다 (0-B)
- **사람이 시트를 읽을 수 있는가** — 생성까지만 검증합니다. 실물 판정은 0-B
- **게이트 기준 재조정** — 재기만 하고 판단은 사람에게 넘깁니다
