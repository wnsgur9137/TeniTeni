# SPEC-0126. 세션과 클립을 지운다

> 이슈 [#126](https://github.com/wnsgur9137/TeniTeni/issues/126)

## 배경

`SessionRepository.delete(id:)`가 구현돼 있고 테스트도 있습니다(`SwiftDataSessionRepository.swift:66`). **호출자가 없습니다.**

[IA-FLOW 10.6](../06-디자인/IA-FLOW.md)이 "잘못 찍힌 클립 → 보관함 스와이프 / 리플레이 메뉴 → 삭제"로 정했고, [SPEC-0116](SPEC-0116-session-library.md)이 스와이프 삭제를 범위 밖으로 돌린 이유가 **"되돌릴 수 없는 동작이라 확인 흐름과 함께 다뤄야 한다"**였습니다.

그래서 지금 **찍은 영상을 앱에서 지울 수단이 전혀 없습니다.** 120fps 클립은 분당 용량이 크고, 디스크가 한 방향으로만 찹니다. [#124](https://github.com/wnsgur9137/TeniTeni/issues/124)(저장공간)가 "보관함 정리"로 사용자를 보내는데 **정리할 수단이 없습니다.**

## 범위

### 만들 것

- **보관함 행 스와이프 → 세션 삭제**
- **리플레이에서 클립 하나 삭제**
- **확인 다이얼로그** — 지울 것을 적어서 보여준다
- **레코드와 파일을 함께 지운다** — `.mov` + 오버레이 사이드카(`.overlay.json`·`.overlay.error`)
- 마지막 클립을 지우면 **세션도 사라진다**
- 마지막 세션을 지우면 보관함이 **빈 상태로** 떨어진다

### 만들지 않을 것

| 항목 | 왜 |
|---|---|
| **되돌리기(스낵바)** | 아래 선택지 2. 지연 삭제가 "보이지만 살아 있는" 상태를 만든다 |
| 여러 개 선택 삭제 | 한 번에 하나로 시작한다. 쌓인 뒤에 필요해지면 그때 넓힌다 |
| 휴지통 | 되돌리기와 같은 문제에 저장공간을 더 쓴다 — #124와 정면으로 어긋난다 |
| 자동 정리 (오래된 것부터) | 사용자가 고르지 않은 삭제다. 가장 되돌리기 어려운 종류를 자동으로 하지 않는다 |
| 보관함 정리 **화면** | #124가 보낼 목적지는 보관함 **그 자체**다. 새 화면을 만들지 않는다 |
| 세션 일부 스윙만 삭제 | 스윙은 클립 안의 구간이다. 영상을 자르는 일이고 범위가 다르다 |

## 구현 선택지

### 1. 삭제를 누가 하는가

레코드(SwiftData)와 파일(`.mov` · 사이드카)을 **함께** 지워야 합니다.

| 선택지 | 장점 | 단점 |
|---|---|---|
| **`Domain` 유스케이스 + 파일 저장소 주입** | 지우는 순서를 한 곳에 둔다. [D-03](../05-결정/stack/D-03-architecture-pattern.md)의 의존 방향을 지킨다 | 추상 하나가 늘어난다 |
| 저장소가 파일까지 지운다 | 호출부가 단순하다 | **`Data`가 `Documents` 경로 규칙과 사이드카 이름 규칙을 알게 된다.** 사이드카 이름 규칙([#121](https://github.com/wnsgur9137/TeniTeni/issues/121))이 `Presentation`과 `Data` 두 곳에 생겨 **둘이 어긋날 수 있다** |
| 호출자가 파일, 저장소가 레코드 | 구조를 가장 적게 바꾼다 | 지우는 순서가 **호출자마다 달라질 수 있다.** 보관함과 리플레이 두 곳에서 같은 순서를 각각 지켜야 한다 |

**채택: `Domain` 유스케이스 + 파일 저장소 주입.**

```
Domain        DeleteSessionUseCase · DeleteClipUseCase
              protocol ClipFileStore { func remove(fileName: String) }
Data          SessionRepository — 레코드만
Presentation  ClipFileStore 구현 (ClipLocator·OverlaySidecarStore 재사용)
```

`ClipLocator`가 이미 그 추상의 절반입니다 — 파일 이름을 URL로 바꾸는 쪽을 들고 있습니다. 지우는 쪽을 더합니다.

### 2. 삭제 순서 — 파일을 먼저 지운다

**어느 쪽이 먼저냐가 "실패했을 때 남는 상태"를 정합니다.**

| 순서 | 실패하면 남는 것 | 그 상태의 성질 |
|---|---|---|
| 레코드 먼저 | **고아 `.mov`** | **사용자에게 보이지 않는다.** 공간만 먹고, [#125](https://github.com/wnsgur9137/TeniTeni/issues/125)가 나중에 주워야 한다 |
| **파일 먼저** | 파일 없는 레코드 | [#120](https://github.com/wnsgur9137/TeniTeni/issues/120)이 **"영상이 없습니다"로 정직하게 보여주는 상태.** 사용자가 다시 지울 수 있다 |

**채택: 파일 먼저.**

보이지 않는 쓰레기보다 **보이는 빈 껍데기**가 낫습니다. 후자는 사용자가 스스로 치울 수 있고, 전자는 알 수조차 없습니다.

> 사이드카도 파일입니다. `.mov` → 사이드카 → 레코드 순으로 지웁니다. 사이드카만 남아도 [#121](https://github.com/wnsgur9137/TeniTeni/issues/121)이 "클립과 짝이 맞는지"를 보고 거부하므로 해롭지 않습니다.

### 3. 되돌리기 — 두지 않는다

| 선택지 | 장점 | 단점 |
|---|---|---|
| **확인만 받고 즉시 지운다** | 구현이 짧다. "지워진 것처럼 보이는데 살아 있는" 상태가 없다 | 실수하면 돌이킬 수 없다 |
| 스낵바 되돌리기 (지연 삭제) | 실수를 살린다 | **상태가 하나 늘어난다** — 아래 |

**채택: 확인만 받고 즉시 지웁니다.**

지연 삭제는 "목록에서는 사라졌는데 디스크에는 있는" 구간을 만듭니다. 그 구간에서 갈리는 것이 셋입니다.

- **앱이 죽으면** 되살릴지 지울지 다시 정해야 한다
- **보관함을 다시 읽으면** 숨길 목록을 따로 들어야 한다
- **[#124](https://github.com/wnsgur9137/TeniTeni/issues/124)가 남은 용량을 셀 때** 아직 안 지워진 용량을 어떻게 셀지가 또 갈린다

**지울 것을 적어서 보여주는 것이 되돌리기보다 쌉니다.**

```
┌──────────────────────────┐
│ 이 세션을 지울까요?        │
│                          │
│ 11월 1일 · 벽치기          │
│ 스윙 12개 · 클립 3개        │
│ 영상을 함께 지우고,         │
│ 되돌릴 수 없습니다.          │
│                          │
│      [취소]   [지우기]      │
└──────────────────────────┘
```

**무엇이 사라지는지 숫자로 적습니다.** "정말 지울까요?"만 묻는 것은 확인이 아니라 절차입니다.

### 4. 마지막 클립을 지우면 세션도 사라진다

| 선택지 | 장점 | 단점 |
|---|---|---|
| **세션도 함께 사라진다** | 보관함에 모호한 행이 남지 않는다 | 촬영 날짜 기록이 사라진다 |
| 세션은 남는다 | 촬영한 사실이 기록으로 남는다 | **#120이 만든 "영상이 없습니다" 행이 두 가지를 뜻하게 된다** |

**채택: 세션도 함께 사라집니다.**

빈 세션을 남기면 보관함에 [#120](https://github.com/wnsgur9137/TeniTeni/issues/120)이 방금 만든 행이 뜹니다.

```
┌────────────────────────┐
│ 11월 1일          12 │
│ ⚠ 영상이 없습니다   스윙 │
└────────────────────────┘
```

**이 행이 뜨는 이유가 둘이 됩니다** — 파일이 사라졌거나(iOS 정리·백업 복원·파일 앱), 내가 지웠거나. 둘을 구분하려면 레코드에 "지운 것"을 적어야 하고, 그러면 **필드와 화면 상태가 하나씩 더 늘어납니다.**

지워지면 그 행이 없습니다. 모호함도 없습니다.

> **마지막 클립을 지울 때는 한 번 더 말합니다** — "마지막 클립입니다. 세션도 지워집니다." 세션이 사라지는 것을 모르고 지우면 그것이 가장 나쁜 실수입니다.

### 5. 스와이프만 둘지, 메뉴도 둘지

보관함은 **스와이프**(IA-FLOW 10.6), 리플레이는 **메뉴**로 정해져 있습니다. 둘을 바꾸지 않습니다.

리플레이의 삭제는 **지금 보는 클립**을 지웁니다 — 스윙이 아니라 클립입니다. 스윙은 클립 안의 구간이고 그것만 지우는 것은 영상을 자르는 일입니다(범위 밖).

지운 뒤 리플레이는 **닫습니다.** 다음 클립으로 넘기면 "방금 지운 것"과 "다음 것"의 경계가 흐려지고, 지운 클립의 스윙이 플레이리스트에서 빠지면서 "34개 중 12번째"의 분모가 화면 안에서 바뀝니다.

## 데이터 모델

```
Domain
  protocol ClipFileStore: Sendable
    func remove(fileName: String) async        파일과 사이드카를 지운다. 실패를 던지지 않는다

  DeleteSessionUseCase(repository:, files:)
    execute(session) async throws              파일 전부 → 레코드
  DeleteClipUseCase(repository:, files:)
    execute(session, clipID) async throws      파일 → 레코드 갱신 (또는 세션 삭제)

DeleteTarget                                   확인 다이얼로그가 읽는 값
  title        String                          "이 세션을 지울까요?"
  detail       String                          "11월 1일 · 벽치기"
  counts       String                          "스윙 12개 · 클립 3개"
  isLastClip   Bool                            마지막 클립이면 경고를 더 적는다
```

`ClipFileStore.remove`가 **실패를 던지지 않는 이유**: 파일이 이미 없는 것은 실패가 아닙니다([#120](https://github.com/wnsgur9137/TeniTeni/issues/120)의 상태). 던지면 호출부가 "없어서 못 지웠다"와 "있는데 못 지웠다"를 구분해야 하는데, **둘 다 결과가 같습니다** — 그 파일은 이제 없습니다.

## 완료 기준

- [ ] `DeleteSessionUseCase`가 **파일을 먼저, 레코드를 나중에** 지운다 — 순서가 값으로 고정된다
- [ ] 레코드 삭제가 실패해도 **파일은 지워진 상태**다 (되돌리지 않는다)
- [ ] 클립 하나를 지우면 그 클립의 `.mov`와 **사이드카 둘**(`.overlay.json`·`.overlay.error`)이 함께 사라진다
- [ ] **마지막 클립을 지우면 세션도 사라진다**
- [ ] 마지막 세션을 지우면 보관함이 **빈 상태**로 떨어진다 (읽기 실패가 아니다)
- [ ] 확인 다이얼로그가 **지울 것을 숫자로** 적는다
- [ ] 마지막 클립일 때 **경고 문구가 다르다**
- [ ] 리플레이에서 지우면 **닫힌다**
- [ ] 파일이 이미 없어도 삭제가 성공한다 (#120의 상태)
- [ ] `scripts/verify-ios.sh` 통과, 이 PR이 늘린 경고 0
- [ ] `scripts/verify-docs.sh` 통과
- [ ] 뮤테이션: 삭제 순서 뒤집기 · 사이드카 삭제 제거 · 마지막 클립의 세션 삭제 제거 · 확인 다이얼로그의 숫자 제거 · 마지막 클립 경고 제거 — **전부 테스트가 죽인다**

## 리스크

| 리스크 | 영향 | 대응 |
|---|---|---|
| 사용자가 실수로 지운다 | **되돌릴 수 없다** | 지울 것을 숫자로 적는다. 마지막 클립은 한 번 더 말한다. 그 이상은 두지 않는다 — 되돌리기의 대가가 더 크다 |
| 레코드 삭제가 실패해 빈 껍데기가 남는다 | 목록에 "영상이 없습니다"가 뜬다 | **#120이 이미 정직하게 보여주는 상태다.** 사용자가 다시 지울 수 있다 |
| 삭제 중 앱이 죽는다 | 파일은 지워지고 레코드는 남는다 | 같은 상태다. 위와 같이 다룬다 |
| 스와이프가 실수로 발동한다 | 확인 다이얼로그가 막는다 | iOS 기본 스와이프 임계를 그대로 쓴다. 더 둔하게 만들지 않는다 |
| 지운 세션을 #124가 아직 셈한다 | 용량 계산이 틀린다 | 즉시 삭제이므로 생기지 않는다 — **되돌리기를 두지 않은 이유 중 하나다** |
