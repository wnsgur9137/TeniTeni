# SPEC-0120. 파일이 없는 클립을 목록이 말한다

> 이슈 [#120](https://github.com/wnsgur9137/TeniTeni/issues/120)

## 배경

보관함([SPEC-0116](SPEC-0116-session-library.md))과 세션 요약([SPEC-0110](SPEC-0110-session-summary.md))은 **SwiftData 레코드만 읽습니다.** 클립의 `fileName`이 가리키는 파일이 실제로 있는지는 확인하지 않습니다.

파일이 없어지는 경로는 실재합니다 — 사용자가 파일 앱에서 지우거나, 저장공간 부족으로 iOS가 정리하거나, 기기 이전·백업 복원에서 레코드만 오거나, 녹화 중 크래시로 레코드만 남습니다.

그래서 목록은 **"스윙 12개"라고 말하고 열면 재생할 것이 없습니다.** [#116의 레퍼런스 조사](../08-레퍼런스/SwingVision.md)에서 반복된 불만이 "찾기 어렵다"가 아니라 **"사라졌다"**였고, 목록이 있다고 말한 것을 못 보여주는 것이 그 불만의 가장 나쁜 형태입니다.

[#123](https://github.com/wnsgur9137/TeniTeni/issues/123)이 **리플레이에는** 이 확인을 넣었습니다(`ClipLocator` + `ReplayMissing` 화면). 남은 것은 **그 앞 단계**입니다 — 목록과 요약은 여전히 거짓을 말합니다.

## 범위

### 만들 것

- **보관함 목록이 클립 파일 존재를 확인**하고, 없으면 그 사실을 행에 적는다
- **세션 요약도 같은 확인**을 한다 — 클립 머리마다
- 결손을 세 단계로 구분: 전부 있음 / 일부 없음 / 전부 없음
- `ClipLocator`를 재사용한다. 새로 만들지 않는다
- [IA-FLOW 10.6](../06-디자인/IA-FLOW.md) 예외 표에 **"클립 파일 결손" 행 추가** — 지금 그 행이 없다

### 만들지 않을 것

| 항목 | 왜 |
|---|---|
| **스윙 수를 재생 가능한 수로 바꾸기** | 아래 선택지 2. 찍은 사실은 지워지지 않았다 |
| 레코드 자동 삭제 | 파일이 돌아올 수 있다(백업 복원·파일 앱에서 되돌리기). 지우는 것은 사용자가 한다([#126](https://github.com/wnsgur9137/TeniTeni/issues/126)) |
| 파일 복구·재다운로드 | 원본이 없다. iCloud 동기화는 Phase 2다 |
| 결손 알림 | 사용자가 목록을 열지도 않았는데 알릴 이유가 없다 |
| 진척도 탭의 집계 보정 | 2-E가 그 탭을 만든다. 지금 빈 화면이다 |
| 오버레이 사이드카 결손 | [#121](https://github.com/wnsgur9137/TeniTeni/issues/121)이 "분석 전"으로 이미 다룬다 |

## 구현 선택지

### 1. 어디서 확인하는가

| 선택지 | 장점 | 단점 |
|---|---|---|
| **보관함 목록에서** | **목록이 거짓을 말하는 시간이 0이다** | 탭 진입마다 파일을 본다 |
| 리플레이가 열 때만 | 추가 읽기가 0. 이미 동작한다 | **눌러 봐야 안다** — 이 이슈가 지적한 바로 그 불만 |
| 요약에서 | 클립 목록이 거기 있다 | 요약도 목록에서 눌러야 열린다 — 한 단계만 짧아진다 |
| 저장 시점에 검증하고 레코드에 표시 | 읽기가 안 느려진다 | **저장 후에 지워지는 경로를 못 잡는다** — 그것이 주된 경로다 |

**채택: 보관함 목록에서.**

[SPEC-0116의 리스크 표](SPEC-0116-session-library.md)가 이것을 범위 밖으로 돌린 근거는 이것입니다.

> 파일 존재 확인은 리플레이가 할 일이고, **목록이 파일을 열면 진입이 느려진다.**

**"연다"와 "있는지 본다"는 다릅니다.** 여는 것(`AVURLAsset` 생성·트랙 로드)은 비쌉니다 — 그 문장은 그 경우에 맞습니다. 그런데 필요한 것은 `stat` 한 번(`FileManager.fileExists`)이고, 파일을 열지 않습니다.

**재 봤습니다.**

```
실측 (macOS SSD, 캐시 더움)
  fileExists 200회 (절반 없음)   0.709 ms
  fileExists 1000회            1.715 ms
```

세션 20개 × 클립 10개 = 200회가 **1 ms 미만**입니다. 보관함은 이미 탭 진입마다 `loadAll()`로 SwiftData를 조회하므로([SPEC-0116 선택지 3](SPEC-0116-session-library.md)), 추가되는 것은 그 조회에 비해 작습니다.

> ⚠️ **이 숫자는 맥입니다.** 실기기 스토리지와 콜드 캐시는 더 느리고, 같은 자리수라고 **우리가 보장하지 않습니다.** 측정은 [#129](https://github.com/wnsgur9137/TeniTeni/issues/129)로 넘깁니다. 다만 "탭 진입이 느려진다"를 **숫자 없이 믿고 정직함을 포기하던 상태**는 끝냅니다.

확인은 **백그라운드에서** 합니다. 메인 액터에서 200회를 돌면 그 1 ms가 프레임 예산 안에 들어갑니다.

### 2. 스윙 수를 어떻게 말하는가

| 선택지 | 장점 | 단점 |
|---|---|---|
| **기록된 수 그대로 + 경고** | 찍은 사실은 지워지지 않았다. 사용자가 세던 수와 맞는다 | 수와 재생 가능한 것이 다르다 |
| 재생 가능한 수로 바꿔 표시 | 지금 보여질 수 있는 것과 정확히 일치 | **사용자가 기억하는 촬영 횟수와 어긋난다.** 누적 집계가 전부 바뀌고, 진척도(2-E)에서 숫자가 뒤로 줄어들어 보인다 |

**채택: 기록된 수 그대로 두고 경고를 붙입니다.**

[#123](https://github.com/wnsgur9137/TeniTeni/issues/123)이 "파일이 없는 칸에서도 **넘기기는 살아 있고 분모를 지킨다**"로 정한 것과 같은 판단입니다 — 건너뛰면 "34개 중 12번째"의 분모가 달라져 사용자가 세던 수와 어긋납니다.

**수를 바꾸는 것은 기록을 고치는 것**이고, 기록은 틀리지 않았습니다. 틀린 것은 "그것을 지금 보여줄 수 있다"는 암시입니다. 그 암시만 거둡니다.

### 3. 결손을 몇 단계로 구분하는가

세션 하나에 클립이 여럿이므로 **일부만 없을 수 있습니다.** 그 둘을 합치면 "영상이 없습니다"가 클립 9개 중 1개가 없는 세션에도 붙습니다.

```
ClipAvailability
  .all        전부 있다          → 아무것도 적지 않는다
  .partial    일부 없다          → "영상 일부 없음"
  .none       전부 없다          → "영상이 없습니다"
```

`.none`과 `.partial`을 **다른 문구로** 적습니다. `.none`은 열어도 볼 것이 하나도 없고, `.partial`은 열면 일부가 재생됩니다 — 사용자가 열지 말지를 그 한 줄로 판단합니다.

### 4. 확인 결과를 어디에 두는가

| 선택지 | 장점 | 단점 |
|---|---|---|
| **화면 상태에 함께 담는다** | 레코드를 건드리지 않는다. 다시 읽을 때마다 새 값이다 | 화면마다 확인한다 |
| SwiftData 레코드에 쓴다 | 한 번만 확인한다 | **파일이 돌아오면 거짓이 된다.** 쓰기가 생겨 읽기 전용이던 경로가 바뀐다 |
| 메모리 캐시 | 탭을 다시 열 때 빠르다 | 그 사이에 지워진 것을 못 잡는다 — 이 이슈가 다루는 상황이 그것이다 |

**채택: 화면 상태에 담습니다.** 파일 존재는 **지금 사실**이고 기록이 아닙니다.

### 5. 요약에서도 확인한다

보관함만 고치면 **요약이 여전히 거짓을 말합니다.** 요약은 클립 머리마다 "클립 1 · 120fps · 스윙 3개"를 적고 그 아래 스윙 행을 깝니다([#123](https://github.com/wnsgur9137/TeniTeni/issues/123)).

클립 머리에 결손을 적고, **그 클립의 스윙 행은 탭해도 리플레이를 열지 않습니다.** 열면 `ReplayMissing`이 뜨는데, **열리기 전에 알 수 있으면 여는 비용을 치를 이유가 없습니다.**

> 리플레이의 `ReplayMissing`은 **그대로 둡니다.** 요약을 보는 사이에 파일이 지워질 수 있고, 그때 마지막 그물이 됩니다.

## 데이터 모델

```
ClipAvailability   all | partial | none        (Presentation)

ClipAvailability.of(_ session: Session, locator: ClipLocator) -> ClipAvailability
  클립이 0개면 .all           ← 스윙 0개 세션은 결손이 아니다
  전부 찾으면 .all
  하나도 못 찾으면 .none
  그 사이면 .partial
```

`Domain`에 두지 않습니다 — 파일 시스템을 보는 판단이고, `Domain`은 저장 매체를 모릅니다([D-03](../05-결정/stack/D-03-architecture-pattern.md)).

## 완료 기준

- [ ] `ClipAvailability.of`가 **값으로 전수 검증**된다 — 클립 0개 / 전부 있음 / 일부 없음 / 전부 없음
- [ ] 클립이 0개인 세션이 `.none`이 **아니다** (스윙 0개 세션은 결손이 아니다)
- [ ] 보관함 목록이 `.partial`과 `.none`을 **다른 문구로** 적는다
- [ ] 스윙 수가 **바뀌지 않는다** — 기록된 값 그대로
- [ ] 요약의 클립 머리가 결손을 적고, 그 클립의 스윙 행이 **열리지 않는다**
- [ ] 확인이 **백그라운드에서** 돈다 — 메인 액터에서 200회를 돌지 않는다
- [ ] 목록을 다시 읽으면 결손도 다시 확인된다 (캐시하지 않는다)
- [ ] `scripts/verify-ios.sh` 통과, 이 PR이 늘린 경고 0
- [ ] `scripts/verify-docs.sh` 통과
- [ ] 뮤테이션: 클립 0개 가드 제거 · `.partial`/`.none` 구분 제거 · 스윙 수를 재생 가능한 수로 교체 · 결손 클립의 탭 차단 제거 — **전부 테스트가 죽인다**

## 리스크

| 리스크 | 영향 | 대응 |
|---|---|---|
| 실기기 읽기가 맥보다 훨씬 느리다 | 탭 진입이 체감된다 | 백그라운드에서 돈다. 목록은 **확인 전에 먼저 그려지고** 결손 표시가 나중에 붙는다 — 느려도 멈추지 않는다 |
| 세션·클립이 아주 많다 | 확인 횟수가 는다 | 클립 수에 비례한다. 보관함이 페이지네이션을 하면 그때 범위도 줄어든다(지금은 전부 읽는다) |

| 결손 표시가 "앱이 지웠다"로 읽힌다 | 신뢰 하락 | 문구에 **"찍은 영상이 지워진 것은 아닙니다"**를 쓰지 않는다 — 이 경우는 실제로 파일이 없다. `LibraryEmpty`의 읽기 실패 문구와 **구분**한다 |
