# SPEC-0116. 보관함 세션 목록

> 이슈 [#116](https://github.com/wnsgur9137/TeniTeni/issues/116)

## 배경

[SPEC-0110](SPEC-0110-session-summary.md)이 **세션 요약**을 세웠습니다. [IA-FLOW 10.3](../06-디자인/IA-FLOW.md)은 보관함과 촬영 직후를 **"같은 목적지"**로 정했고, 그래서 `SessionSummaryFeature`는 세션을 통째로 받지 않고 **`id`만 받아 스스로 읽습니다.** 목적지는 섰고 입구 하나가 비어 있습니다.

지금 보관함 탭은 `LibraryPlaceholderView`를 그립니다. 그 결과 **앱을 끄면 찍은 것에 다시 닿을 길이 없습니다.** 요약은 촬영 직후 한 번 열리고 닫으면 끝입니다.

`SessionRepository.loadAll()`은 구현과 테스트가 있는데 **호출자가 없습니다.** 이 작업이 첫 호출자가 됩니다.

### 레퍼런스가 범위를 바꿨다

[SwingVision 2026-10-27절](../08-레퍼런스/SwingVision.md)의 조사에서 찾으려던 것은 "목록이 길어졌을 때의 탐색 불만"이었고 **그것은 나오지 않았습니다.** 대신 전혀 다른 축이 반복됩니다 — TennisCut은 크래시로 녹화가 통째로 사라지고, SwingVision은 업로드 손상을 겪고 녹화 **전에** 저장공간을 경고하도록 바꿨고, Hudl Technique은 종료 시 이관하지 않은 영상을 삭제했습니다.

**보관함의 첫 일은 탐색이 아니라 "찍은 것이 살아 있다는 증거"입니다.** 그래서 이 작업은 필터·썸네일을 미루고 **빈 상태와 읽기 실패를 구분해 보여주는 것**을 먼저 둡니다.

## 범위

### 만들 것

- `LibraryFeature` — `loadAll()`로 세션을 읽고 `loading / loaded / failed`로 갈린다
- `LibraryView` — 세션 행: 날짜·시각 · 상황 · 스윙 수 · 클립 수 · fps
- **빈 상태** — "아직 찍은 것이 없습니다" + 촬영 탭으로 보내는 버튼
- **읽기 실패 상태** — 사유 + 다시 시도. 빈 목록으로 위장하지 않는다
- 행을 누르면 **기존 `SessionSummaryFeature`**가 열린다 (`Application` 코디네이터 경유)
- 탭으로 돌아올 때 다시 읽는다 — 촬영하고 보관함으로 오면 방금 세션이 있어야 한다

### 만들지 않을 것

| 항목 | 왜 |
|---|---|
| 유형 필터 | 유형은 1-D 분류가 만든다. **지금은 필터할 축이 없다.** IA-FLOW 10.2의 "세션 목록(유형 필터)"은 1-D 이후다 |
| 스와이프 삭제 | 되돌릴 수 없는 동작이다. [IA-FLOW 10.6](../06-디자인/IA-FLOW.md)의 예외 화면 묶음에서 확인 흐름과 함께 다룬다 |
| 클립 썸네일 | 통영상에서 프레임을 꺼내야 하고, 목록이 길어질 때의 성능 문제를 같이 들고 온다 |
| 스윙 리플레이 | 1-E의 별 작업이다. 요약까지 닿으면 이 작업은 끝이다 |
| 검색·정렬 | 조사에서 근거가 나오지 않았다. 세션이 쌓인 뒤에 실물로 판단한다 |
| 페이지네이션 | `loadAll()`이 전부 읽는다. 상한을 정할 근거(실제 세션 개수)가 없다. 리스크 절에 적는다 |

## 구현 선택지

### 1. 목록이 세션을 들고 요약에 넘기는가

| 선택지 | 장점 | 단점 |
|---|---|---|
| **id만 넘긴다** | 촬영 직후와 **같은 코드**를 쓴다. 저장이 실제로 됐는지 그 읽기로 드러난다 | 같은 세션을 두 번 읽는다 |
| `Session`을 넘긴다 | 읽기 한 번 | 입구마다 다른 코드가 된다. SPEC-0110이 그러지 않기로 한 이유를 되돌린다 |

**채택: id만 넘긴다.** 두 번 읽는 비용은 SwiftData 한 건 조회이고, 입구가 둘로 갈리는 비용은 영구적입니다.

### 2. 목록 상태를 어디에 두는가

| 선택지 | 장점 | 단점 |
|---|---|---|
| **`AppFeature`의 자식 `LibraryFeature`** | D-03을 지킨다 — 요약 열기는 코디네이터가 한다 | `AppFeature`가 조금 더 커진다 |
| `LibraryFeature`가 요약을 직접 띄운다 | 배선이 짧다 | **D-03 위반** — Feature 간 직접 의존 |

**채택: 코디네이터 경유.** `LibraryFeature`는 `.delegate(.sessionTapped(id))`만 올리고, `AppFeature`가 `summary`를 엽니다. 요약의 `fullScreenCover`는 이미 `tabs`에 붙어 있으므로([AppView](../../ios/Projects/Application/Sources/AppView.swift)) 추가 앵커가 필요 없습니다.

### 3. 언제 다시 읽는가

| 선택지 | 장점 | 단점 |
|---|---|---|
| **탭 진입마다 (`.task`)** | 촬영 직후 보관함으로 오면 방금 세션이 보인다 | 탭을 오갈 때마다 읽는다 |
| 한 번만 읽고 캐시 | 읽기가 적다 | **방금 찍은 것이 안 보인다** — 이 작업의 존재 이유를 깬다 |
| 저장소가 변경을 알린다 | 정확하다 | `SessionRepository`에 관측 경로를 새로 낸다. 범위가 커진다 |

**채택: 탭 진입마다.** SwiftData 조회 한 번이고, "방금 찍은 것이 없다"는 이 화면에서 가장 나쁜 실패입니다.

### 4. 정렬

최신이 위입니다. `startedAt` 내림차순으로 **뷰가 아니라 Feature에서** 정렬합니다 — 저장소의 반환 순서에 기대면 그 순서가 바뀔 때 조용히 깨집니다.

## 리스크

| 리스크 | 영향 | 대응 |
|---|---|---|
| `loadAll()`이 전부 읽는다 | 세션이 수백 개면 탭 진입이 느려진다 | **지금은 측정할 수 없다** — 실기기에 세션이 쌓인 뒤 판단한다. 상한을 추측해 넣지 않는다 |
| 탭 진입마다 읽어 조회가 늘어난다 | SwiftData 조회 한 번. 체감 없음 | 실기기에서 느리면 저장소 관측 경로로 바꾼다 (선택지 3의 세 번째) |
| 세션 레코드는 있는데 클립 **파일**이 없다 | 목록에는 보이는데 열면 재생할 것이 없다 | **이 작업 범위 밖이다.** 파일 존재 확인은 리플레이가 할 일이고, 목록이 파일을 열면 진입이 느려진다. 별도 이슈로 올린다 |
| 조사에서 탐색 불만이 안 나온 것을 "탐색은 문제가 아니다"로 읽기 | 필터·검색을 영구히 미룬다 | 레퍼런스 절에 **검색 3회로 나오지 않았을 뿐**임을 적었다. 1-D 이후 다시 본다 |
