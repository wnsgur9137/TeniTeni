# 08. 로드맵과 리스크

## 8.1 단계별 계획

| Phase | 목표 | 백엔드 | 예상 기간 | 게이트 |
|---|---|---|---|---|
| **0** | 기술 검증 프로토타입 | ✗ | 2~3주 | **공 궤적 검출률 70%** |
| **1** | 온디바이스 완결 제품 | ✗ | 4~6주 | 스윙 검출 95%, 분류 90% |
| **2** | 백엔드 연동 | ✓ | 4~6주 | 피드백 오지적률 10% 미만 |
| **3** | 코트 분석 + 레퍼런스 비교 | ✓ | 6주+ | — |

### Phase 0 — 기술 검증

**목표: 이 앱이 기술적으로 가능한지 판정한다.**

- [ ] AVCaptureSession 구성, 60/120fps 포맷 선택
- [ ] `VNDetectHumanBodyPoseRequest` 연결, 스켈레톤 오버레이 (좌표 변환 포함)
- [ ] One Euro Filter 적용
- [ ] `VNDetectTrajectoriesRequest` 연결, 궤적 트레일 표시
- [ ] **실제 코트에서 촬영해 궤적 검출률 측정**
- [ ] 프레임 시간 프로파일링

백엔드 코드는 한 줄도 쓰지 않습니다. Tuist 모듈 분리도 하지 않습니다. 단일 타깃에 전부 넣어도 됩니다.

> **게이트: 궤적 검출률이 70%에 못 미치면 접근 방식을 재설계합니다.**
> 서버 기반 TrackNet으로 전환하거나, 궤적 기능을 v1 범위에서 제외하는 판단이 필요합니다.
> 이 검증 전에 다른 작업에 착수하면 매몰 비용만 커집니다.

### Phase 1 — 온디바이스 완결 제품

- [ ] Tuist 모듈 구조로 재편
- [ ] 스윙 구간 자동 검출 (룰 + 히스테리시스)
- [ ] 학습 데이터 촬영 (유형별 200회+)
- [ ] Create ML Action Classifier 학습 및 통합
- [ ] 페이즈 분할, 임팩트 프레임 특정
- [ ] 메트릭 산출 + 룰 엔진 피드백
- [ ] 링 버퍼 기반 스윙 구간 저장
- [ ] 리플레이 화면 (슬로우 모션 + 스켈레톤 + 피드백)
- [ ] 로컬 DB, 세션 요약
- [ ] 골든 테스트 구축

이 시점에서 **앱은 이미 혼자서 유용합니다.** 백엔드 없이 TestFlight 배포가 가능한 상태여야 합니다.

### Phase 2 — 백엔드 연동

- [ ] Sign in with Apple + 세션 토큰
- [ ] presigned URL 업로드, 백그라운드 전송
- [ ] 분석 워커 (비동기 큐)
- [ ] 서버 정밀 분석이 온디바이스 대비 유의미한지 **정량 검증** → 미달이면 축소
- [ ] 진척도 집계 및 차트
- [ ] 기기 간 동기화
- [ ] 개인정보 처리방침, ATT 대응

### Phase 3 — 확장

- [ ] 코트 라인 검출 + 호모그래피
- [ ] 바운스 지점, 인/아웃, 구속 추정
- [ ] 프로 레퍼런스 라이브러리
- [ ] DTW 기반 비교 + 고스트 오버레이
- [ ] Metal 프리뷰 렌더로 지연 제거
- [ ] (검토) Apple Watch IMU 연동

## 8.2 리스크 레지스터

| ID | 리스크 | 영향 | 확률 | 대응 |
|---|---|---|---|---|
| R-1 | **공 궤적 검출 실패** | 치명적 | 중 | Phase 0에서 최우선 검증. 실패 시 서버 TrackNet 또는 기능 제외 |
| R-2 | **카메라 흔들림** | 높음 | 높음 | UX로 승격 — 삼각대 안내, 프레이밍 가이드, 가속도계 흔들림 감지 및 경고 |
| R-3 | **자세 평가 신뢰도** | 높음 | 높음 | 룰 엔진 + 코치 자문. 신뢰도 낮으면 단정하지 않는 UX |
| R-4 | **학습 데이터 부족** | 높음 | 중 | 자체 촬영 + 증강 + 공개 데이터셋. 초기엔 룰 기반으로 우회 |
| R-5 | **발열/스로틀링** | 중간 | 높음 | 입력 다운스케일, `thermalState` 감지 후 품질 동적 저하 |
| R-6 | **저장 용량** | 중간 | 높음 | 스윙 구간만 저장, HEVC, 자동 정리 정책 |
| R-7 | **배터리 소모** | 중간 | 높음 | 실측 후 예상 촬영 시간 안내. 외부 배터리 권장 |
| R-8 | **프라이버시 심사** | 중간 | 중 | Phase 2 이전에 처리방침·ATT 준비. 업로드 기본 꺼짐 |
| R-9 | **GPU 서버 비용** | 중간 | 중 | 서버 ML 가치 검증 후 도입. CPU로 시작 |
| R-10 | **1인 개발 범위 초과** | 높음 | 높음 | Phase 0/1을 백엔드 없이 설계한 이유. 단계 게이트 엄수 |

### 상세: R-2 카메라 흔들림

`VNDetectTrajectoriesRequest`는 **고정 카메라가 전제**입니다. 손으로 들고 찍으면 궤적 검출이 완전히 무너집니다. 이건 튜닝으로 해결되지 않습니다.

따라서 기술 제약을 제품 요구사항으로 승격시킵니다:
- 온보딩에서 삼각대 사용을 명시적으로 안내
- 촬영 화면에 권장 거리/각도 프레이밍 가이드
- `CMMotionManager`로 흔들림 감지 → 실시간 경고 배너
- 흔들림이 임계값을 넘으면 궤적 기능을 자동 비활성화하고 이유를 표시

### 상세: R-3 자세 평가 신뢰도

"이 스윙 87점"을 ML로 만들려면 점수 라벨 데이터셋이 필요한데, 존재하지 않습니다. 게다가 프로 선수들의 폼도 서로 크게 달라 정답이 하나가 아닙니다.

대응은 [03. 비전 파이프라인](../02-설계/VISION-PIPELINE.md) 3.6절의 3단계 접근입니다. 핵심은 **틀릴 수 있음을 인정하는 UX**입니다. 신뢰도가 낮은 지적은 단정형으로 표현하지 않습니다.

## 8.3 열린 질문

기술 스택 확정과 별개로 제품 차원에서 답이 필요한 항목입니다.

- [ ] 촬영 각도를 몇 종으로 지원할 것인가? (측면 / 후면 / 정면) — 메트릭 계산식이 각도별로 달라짐
- [ ] 왼손잡이 처리는 좌우 반전으로 충분한가?
- [ ] 세션당 예상 촬영 시간은? (배터리·저장 용량 설계에 직결)
- [ ] 수익 모델은? (무료 / 구독 / 일회성) — 서버 비용 구조에 영향
- [ ] 코치 자문을 어떻게 확보할 것인가? — R-3의 유일한 실질적 해법
- [ ] 라이브 오버레이와 리플레이 중 구현 우선순위 ([04](../02-설계/SKELETON-OVERLAY.md) 4.9절)
