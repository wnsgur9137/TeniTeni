# 09. 작업 순서

> **작업 상태는 [GitHub Issues](https://github.com/wnsgur9137/TeniTeni/issues)에 있습니다.**
> 각 단계는 동명의 마일스톤에 대응합니다. 이 문서는 순서와 선행 관계만 담습니다.

> [!IMPORTANT]
> **열린 작업에는 이슈 번호를 답니다.** 상태는 이슈가 정본이고, 이 문서는 **그 이슈가 어느 자리에 오는지**를 적습니다 — 계획 문서와 이슈 목록을 사람이 머리로 맞추지 않게 하는 것이 목적입니다.
>
> [로드맵](ROADMAP.md)에는 번호를 적지 않습니다. 그쪽은 "무엇을 언제"를 담고, 번호는 순서·선행과 함께 있어야 쓸모가 있습니다.

[로드맵](ROADMAP.md)이 "무엇을 언제"라면, 이 문서는 **"어떤 순서로, 무엇이 선행인지"** 를 정의합니다.

## 9.1 원칙

**1. 게이트를 최대한 앞으로 당긴다**

Phase 0 게이트(궤적 검출률 70%)가 실패하면 그 위에 쌓은 코드가 상당 부분 무의미해집니다. 게이트 판정에 필요한 최소 코드만 먼저 만듭니다.

**2. 검증은 오프라인으로 한다**

궤적 검출률은 실시간으로 잴 필요가 없습니다. 영상을 찍어두고 나중에 돌려도 같은 값이고, 오히려 **파라미터를 바꿔가며 반복 측정**할 수 있습니다. 코트에 여러 번 나가지 않아도 됩니다.

**3. 모듈은 필요할 때 만든다**

Tuist 모듈을 처음부터 다 나누지 않습니다. **각 모듈은 나눠야 할 구체적 이유가 생겼을 때** 도입합니다 (9.5절).

**4. 백엔드는 Phase 2까지 손대지 않는다**

[ADR-0001](../05-결정/adr/ADR-0001-hybrid-inference.md) 오프라인 우선 원칙. 예외는 두 가지뿐입니다 — Protobuf 스키마(Phase 1)와 CI(Phase 0 말).

## 9.3 Phase 0 — 기술 검증

### 0-A. 정찰 (책상, 2~3일)

목표: **실측으로 촬영 프로토콜의 가정을 보정하고, 영상을 찍을 수 있게 만든다.**

| # | 작업 | 산출물 |

| 1 | 실기기 지원 포맷 덤프 ([#4](https://github.com/wnsgur9137/TeniTeni/issues/4) 🚧) | 해상도·fps·binned 목록 |
| 2 | 화각 실측 → [촬영 프로토콜 5.1](../02-설계/CAPTURE-PROTOCOL.md#51-카메라-배치) 계산값 보정 ([#4](https://github.com/wnsgur9137/TeniTeni/issues/4) 🚧) | 공 픽셀 크기 실측표 |
| 3 | **최소 촬영 앱** | 프리뷰 + 녹화 버튼 |

최소 촬영 앱의 범위를 엄격히 지킵니다.

- ✅ `activeFormat`으로 1080p120 / 1080p60 선택
- ✅ `setExposureModeCustom` 노출 고정 (1/1000, 1/500, 1/250 전환 가능)
- ✅ 기본 `AVCaptureVideoPreviewLayer` — Metal 아님
- ✅ 녹화 + 촬영 메타(fps·노출·거리) 파일명에 기록
- ❌ 오버레이, 포즈, 궤적, TCA, 모듈 분리 — **전부 없음**

> 단일 타깃 하나면 됩니다. Tuist를 아직 도입하지 않습니다.

목표: **조건을 변주한 영상 세트 확보.** 이게 이후 모든 작업의 입력이자 골든 테스트 픽스처가 됩니다.

| 변수 | 값 |
|---|---|
| fps | 120, 60 |
| 노출 | 1/1000, 1/500, 1/250 |
| 거리 | 5m, 6m, 8m |
| 배경 | 단순, 복잡(펜스·관중) |
| 조명 | 실외 맑음 (기준), 실외 흐림 |

각 조합마다 최소 10타구. **기준 조건(실외 맑음·단순 배경·120fps·1/1000·6m)은 30타구 이상.**

> 한 번에 다 못 찍어도 됩니다. 기준 조건부터 확보하고 나머지는 0-C 결과를 보며 추가 촬영합니다.

#### 왜 1~5는 게이트와 무관한가

9.8 중단·재검토 지점의 조치는 **"궤적 기능 v1 제외"**이지 앱 전체가 아닙니다. 궤적 검출이 쓸 만하지 않다고 판정돼도 **스켈레톤 오버레이와 1-B 스윙 검출은 남습니다** — 스윙 검출은 손목 각속도 기반이고, 그것은 궤적이 아니라 **포즈**에서 나옵니다.

7·8이 "부분"인 이유는 6번의 렌더 패스가 프레임 예산에 들어가기 때문입니다. 1~5만으로도 프로파일링은 할 수 있지만, **그 숫자가 최종값이 아닙니다.**

#### 실기기 없이 검증되는 것

| 작업 | 실기기 |
|---|---|
| 2 `RenderTransform` | **불필요** — 순수 행렬 수학, 단위 테스트로 전부 고정 |
| 1·3·4·5 | 필요 — 카메라·GPU·실제 회전각이 있어야 확인된다 |

2번을 먼저 하면 실기기를 기다리는 동안에도 진행할 수 있습니다.

설계는 [스켈레톤 오버레이](../02-설계/SKELETON-OVERLAY.md)와 [동시성](../02-설계/CONCURRENCY.md)에 있습니다. 4.10절의 "Phase 0 검증 항목" 체크리스트가 1·2·4·5에 대응합니다.

**병렬 CI 구축**: 0-D 기간에 `ios.yml`을 만들고, 완료 후 [D-22](../05-결정/stack/D-22-repository-workflow.md)의 브랜치 보호를 강화합니다.

## 9.4 Phase 1 — 온디바이스 완결 제품

> **1-A와 1-A′는 게이트를 기다리지 않습니다.** 궤적 검출 성패와 무관하고 카메라도 필요 없습니다 — 0-B 촬영을 기다리는 동안 진행합니다. 근거는 아래 "왜 게이트와 무관한가".

### 1-A. 모듈 재편 + 앱 셸 (1주)

**Tuist 전면 도입 시점.** 9.6절의 구조로 재편합니다. 여기까지는 `TeniVision` + 앱 타깃 정도만 있었습니다.

| # | 작업 |
|---|---|
| 1 | `Domain` · `Data` · `Presentation` · `Application` · `DesignSystem` 모듈 분리 |
| 2 | `Application` 코디네이터 — `TeniTeniApp`이 `CaptureView()`를 직접 띄우는 구조를 바꾼다 |
| 3 | **탭바 3개** (촬영 / 보관함 / 진척도) 골격 |
| 4 | **화면 방향 정리** — 아래 참고 |
| 5 | `DesignSystem` 토큰을 [11장](../06-디자인/DESIGN-SYSTEM.md)에서 코드로 |

#### ⚠️ 세로 방향이 금지돼 있다

현재 `Info.plist`가 가로만 허용합니다.

```xml
<key>UISupportedInterfaceOrientations</key>
<array>
  <string>UIInterfaceOrientationLandscapeLeft</string>
  <string>UIInterfaceOrientationLandscapeRight</string>
</array>
```

0-A는 촬영 화면만 있어 맞았지만 **설계상 세로 화면이 12종**입니다 ([IA-FLOW 10.9](../06-디자인/IA-FLOW.md)). **촬영 화면만 가로 고정**으로 남기고 나머지를 풀어야 합니다.

### 1-A′. 진입 화면 (1주)

**1-B가 이것 없이는 시작되지 않습니다.** [비전 파이프라인 3.3](../02-설계/VISION-PIPELINE.md)이 `dominantHand`를 스윙 검출의 **주 신호**로 쓰는데, 지금 앱에는 그 값을 받을 경로가 없습니다.

| # | 화면 | 아트보드 |
|---|---|---|
| 1 | 온보딩 (배치 안내·권한) | `Main` |
| 2 | **주 사용 손** — 비워둔 채 촬영에 들어갈 수 없다 | `OnboardingHand` |
| 3 | 홈 (촬영 상황 5종 + 시합의 관찰 대상) | `CaptureHome` |
| 4 | 설정 | `Settings` |
| 5 | 진척도 · 보관함 **빈 상태** | — (아래 참고) |

5번은 **탭이 눌리는데 아무것도 안 나오면 앱이 고장난 것처럼 보이기 때문**입니다. 실제 내용은 나중입니다 — 보관함은 1-E, **진척도는 2-E**(Swift Charts, 기간별 집계).

> **아트보드 칸이 비어 있는 이유.** `Progress`·`Library`는 **완성형 목업**이고(2-E·1-E) 5번이 만든 빈 상태가 아닙니다. 보관함 쪽은 1-E에서 `LibraryEmpty`가 따로 생겼고, 진척도 쪽은 아직 없습니다 — [#139](https://github.com/wnsgur9137/TeniTeni/issues/139).

> ✅ **정했습니다 (2026-11-03) — 빈 상태를 다듬어 내보냅니다.** 2-E를 앞당기지 않습니다. 근거는 [1-E 절](#1-e-리플레이-1주)에 적었습니다.

#### 왜 게이트와 무관한가

9.8 중단·재검토 지점의 조치는 **"궤적 기능 v1 제외"** 이지 앱 전체가 아닙니다. 게이트가 실패해도 앱은 스윙 분석으로 가고, **온보딩·홈·설정·탭바는 그대로 필요합니다.**

카메라도 필요 없어 **시뮬레이터에서 검증됩니다** — `ios` 게이트가 이미 시뮬레이터 빌드를 돕니다.

### 1-B. 스윙 검출 (2~3주)

- 손목 각속도 기반 룰 트리거 + 히스테리시스
- 링 버퍼 (소급 저장) — **미완. 아래 참고** ([#103](https://github.com/wnsgur9137/TeniTeni/issues/103))
- 스윙 구간 클립 저장
- `Domain` 엔티티 확정 (Session, Clip, Swing)
- **SwiftData 영속화** — 저장할 곳 없이 클립을 저장할 수 없다. [D-08](../05-결정/stack/D-08-local-db.md)이 "메타데이터만"으로 확정했으므로 영상 파일과 무관하다
- **중간 확인 화면**(`QuickCheck`) — 왕복 빈도 '중간'·'잦음' 상황에서 필요
- **예외 화면** — 스윙 0개 진단(`EmptySession`), 발열 경고(`ThermalWarning`)

#### ⚠️ 링 버퍼는 1차 조치만 들어가 있다 — [#103](https://github.com/wnsgur9137/TeniTeni/issues/103)

`FrameIntake`의 얕은 복사 때문에 링 버퍼 한 장이 `AVCaptureVideoDataOutput` **출력 풀의 한 장을 붙듭니다.** 상한이 없으면 풀이 고갈돼 분석 프레임이 끊기고, 화면에는 "스윙 0개"로만 보입니다.

[#97](https://github.com/wnsgur9137/TeniTeni/issues/97)에서 **1차 조치**가 들어갔습니다 — `ClipRecorder`가 `backlogCapacity`로 장 수 상한을 받고, `SwingPipeline`이 **24장**을 넘깁니다(분석 60fps 기준 0.4초). 상한에 걸려 버린 장 수는 `droppedBacklogCount`로 셉니다. 점유에 증명 가능한 상한이 생겼으므로 **지금 증상은 "스윙이 안 잡힌다"가 아닙니다.**

**대가는 클립의 머리입니다.** 되감을 구간이 `preRoll`(2초)보다 짧아져 **테이크백 대부분이 빠집니다.** 남은 일은 둘입니다.

| 남은 일 | 실기기 |
|---|---|
| 소급분을 캡처 풀 밖으로 옮기는 설계 — 클립 해상도와 맞바꾸는 제품 결정이다 | 불필요 |
| 상한 24가 옳은 값인지 실측 — `AVCaptureVideoDataOutput`은 풀 크기를 공개하지 않는다 | **필요** |

근거는 [SPEC-0097](../07-기획/SPEC-0097-swing-wiring.md) 선택지 2와 그 리스크 표에 있습니다.

#### 진척도 탭은 빈 상태로 내보낸다 (2026-11-03 결정)

1-A′ 절이 "2-E를 앞당길지, 빈 상태를 다듬어 내보낼지는 **1-E에 가서 정한다**"로 남긴 것을 정했습니다.

**빈 상태를 다듬어 내보냅니다.** 2-E를 앞당기지 않습니다.

| 지금 있는 데이터 | 진척도의 핵심인데 **없는** 데이터 |
|---|---|
| 세션 날짜·상황·fps | 유형 분류 (포핸드·백핸드·서브) |
| 스윙 개수·구간·임팩트 시각 | [메트릭 9개](../02-설계/VISION-PIPELINE.md) |
| → "주 3회, 스윙 142개"까지 | 룰 엔진 판정 → **"포핸드가 나아지고 있다"를 못 한다** |

**진척도의 핵심은 유형별 추이이고 그 분류가 1-D에 있습니다.** 지금 만들면 숫자가 없는 차트가 되고, 1-D가 끝나면 그 화면을 **다시 짓게 됩니다.** 게다가 평가 임계값은 코치 자문([#54](https://github.com/wnsgur9137/TeniTeni/issues/54)) 선행이고 그것이 리드타임이 가장 깁니다.

**탭을 없애지도 않습니다.** [IA-FLOW 10.2](../06-디자인/IA-FLOW.md)가 탭 셋을 "찍는다 · 찾는다 · 본다"로 정했고, 1-A′ 5번이 **"탭이 눌리는데 아무것도 안 나오면 앱이 고장난 것처럼 보인다"**는 이유로 빈 상태를 먼저 만들어 둔 것입니다. 그 판단은 그대로 유효합니다.

TestFlight 전에 할 일은 [#139](https://github.com/wnsgur9137/TeniTeni/issues/139)입니다.

#### ⚠️ 위 결정을 적을 때 확인하지 않은 것 (2026-11-03 보정)

이 절은 처음 **"아트보드는 이미 있고(`Progress`), 남은 일은 문구를 다듬는 것뿐"**이라고 적었습니다. 그 화면도 그 문구도 열어보지 않고 쓴 문장이고, **둘 다 틀렸습니다.**

| 적었던 것 | 실제 |
|---|---|
| 아트보드는 이미 있다 | `Progress`는 **2-E 완성형 목업**입니다 — 평균 점수 72, +11, 8주 추이 라인. **TestFlight에 실리는 빈 상태의 목업은 없습니다** |
| 문구를 다듬으면 된다 | 지금 문구는 다듬을 대상이 아니라 **거짓입니다.** `ProgressPlaceholderView`가 `"세션이 쌓이면 나타납니다"`라고 말하는데, 세션이 쌓여도 나타나지 않습니다 — 지표는 1-D, 차트는 2-E입니다 |

그래서 #139는 **더 친절하게 쓰는 일이 아니라 사용자에게 보이는 거짓을 고치는 일**이고, `Progress`를 고치는 일이 아니라 `ProgressEmpty`를 **새로 만드는** 일입니다. `Progress`를 빈 상태로 덮으면 2-E가 참고할 목업이 사라집니다 — `LibraryEmpty`가 `Library`와 따로 있는 것과 같은 이유입니다 ([IA-FLOW 10.10](../06-디자인/IA-FLOW.md)).

**결정 자체는 바뀌지 않습니다** — 2-E를 앞당기지 않습니다. 바뀌는 것은 #139의 크기입니다.

## 9.6 Tuist 모듈 구성

### 목표 구조

```
Application     앱 진입점, DI Composition Root, 라우팅
Presentation    화면 단위 TCA Feature (Capture, Analysis, Session, Library, Progress, Onboarding, Settings)
Domain          Entity, UseCase, Repository 프로토콜 — 의존성 0
Data            Repository 구현, SwiftData 영속화, 파일 저장소
Network         Moya TargetType, DTO, 인증 인터셉터
TeniVision       분석·렌더 엔진 (Pose / Ball / Render / Swing / Metrics)
DesignSystem    컬러·타이포·공용 컴포넌트
Core            Logger, Extensions, 공용 유틸
```

### 의존성 방향

```
        Application
             │
    ┌────────┼────────┐
Presentation  Data ──→ Network
    │  │       │           │
    │  └──→ Domain ←───────┘
    │          ▲
    │      TeniVision
    │          │
DesignSystem   │
    └────→ Core ←───┘
```

**규칙**

- `Domain`은 아무것도 import하지 않는다 (Foundation 제외)
- `TeniVision`은 `Domain` 엔티티와 `Core`만 안다. **UI를 모른다** → macOS CLI에서 재사용 가능
- `Network`는 `Domain`을 모른다. DTO만 다루고 매핑은 `Data`가 한다
- `Presentation` 내 Feature 간 직접 의존 금지. `Application` 코디네이터 경유
- 프레임 스트림은 `Presentation`이 `TeniVision`을 직접 쓴다 ([D-03](../05-결정/stack/D-03-architecture-pattern.md) TCA 바깥 경로)

### 도입 순서 — 필요할 때 만든다

| 시점 | 도입 | 강제 이유 |
|---|---|---|
| 0-A | (단일 타깃) | 모듈 불필요 |
| **0-C** | **TeniVision** ✅ | **macOS CLI와 iOS 앱이 같은 분석 코드를 써야 함** |
| 0-D | Core | 실시간 파이프라인에서 공용 유틸 발생 |
| **1-A** | **Domain, Data, Presentation, Application, DesignSystem** | TCA Feature가 여러 개 생기는 시점 |
| **2-C** | **Network** | 서버 연동 시작. 그전에 만들면 빈 모듈 |

`Network`를 Phase 1에 만들지 않는 이유는 단순합니다 — **넣을 게 없습니다.**

## 9.7 병렬화

| 가능 | 불가 |
|---|---|
| 0-D 파이프라인 ∥ CI 구축 | — |
| **0-D 1~5 (렌더·포즈) ∥ 0-B 촬영 대기** | **0-C 게이트 전에 0-D 6~8 착수** (궤적 의존 — 실패 시 매몰) |
| **1-A·1-A′ (모듈·앱 셸·진입 화면) ∥ 0-B 촬영 대기** | 1-B 이후를 게이트 전에 착수 (검출·데이터·분류가 게이트에 달렸다) |
| 1-C 학습 데이터 촬영 ∥ 1-D 메트릭 구현 | 1-B 없이 1-C (수동 구간 추출은 비효율) |
| 2-B 이후 백엔드 ∥ iOS 2-C | 2-A 없이 2-C (엔드포인트 미정) |
| 코치 자문 확보 ∥ 전 단계 | — |

**Phase 1도 통으로 막지 않습니다.** 1-A(모듈·앱 셸)와 1-A′(진입 화면)는 궤적 검출 성패와 무관하고 카메라도 필요 없습니다. 오히려 **1-B가 진입 화면 없이는 시작되지 않습니다** — `dominantHand`를 받을 경로가 없기 때문입니다.

**0-D를 통으로 막지 않습니다.** 9.3의 0-D 표가 작업별 궤적 의존 여부를 정합니다. 1~5는 궤적 성패와 무관하므로 게이트를 기다리지 않습니다 — #4(실기기)와 0-B(촬영)가 사람의 일정에 달려 있어 **게이트 판정 시점을 예측할 수 없기 때문**입니다.

**코치 자문은 지금부터 병렬로 진행합니다.** [ADR-0003](../05-결정/adr/ADR-0003-rule-based-evaluation.md)의 룰 임계값을 정할 사람이 필요하고, 리드타임이 가장 깁니다. 1-D 시작 전까지 확보되어야 합니다.

## 9.8 중단·재검토 지점

| 지점 | 조건 | 조치 |
|---|---|---|
| **0-C** | 검출률 < 50% | 접근 재설계. 서버 TrackNet 또는 궤적 기능 v1 제외 — **타격이 작아졌습니다**(아래) |
| 1-D | 분류 정확도 < 90% | 데이터 추가 촬영 → 커스텀 모델 검토 |
| 1-D | 코치 자문 미확보 | 룰 임계값을 문헌 기반 잠정값으로 두고 진행, 출시 전 검증 필수 |
| 2-F | 서버 ML 개선폭 미미 | 서버 ML 미도입. 인프라 단순화 |

### 0-C 미달의 타격이 작아졌다

[ADR-0006](../05-결정/adr/ADR-0006-replay-overlay-layers.md) 전에는 궤적이 **실시간 렌더 경로**였습니다. 빠지면 0-D의 렌더 패스 하나와 그것이 전제한 프레임 예산 설계가 함께 흔들렸습니다.

지금은 궤적이 **리플레이 레이어 하나**입니다. 빠지면 모드 목록에서 하나가 사라지고 나머지는 그대로 돕니다 — 스켈레톤과 라켓 궤적은 포즈에서 나오므로 0-C와 무관합니다.
